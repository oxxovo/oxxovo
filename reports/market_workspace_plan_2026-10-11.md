# Market 작업공간 계획 (계획만 -- 코드·SQL·배포 없음)

작성: 지수(메인), 2026-10-12. 파일명은 어제 지시대로 `2026-10-11`. 로컬 작성, 커밋·푸시·배포하지 않음.
**이 문서는 결정이 아니라 선택지와 질문이다.** 아래 "먼저 답이 필요한 4가지"가 비어 있는 동안 데이터 구조는 확정하지 않는다.

**갱신 2026-10-12 (TK님 결정):** 아래 질문 4개(Q1~Q4)는 **마켓 제니가 TK님과 정한다.** 지수는 그 답이 올 때까지 데이터 구조(4절)를 확정하지 않는다. 4절은 선택지 목록으로만 읽는다.

## 1. 지금 있는 것 (실측: `lib/site-nav.ts`, `app/market/page.tsx`, 카탈로그)

- `/market` 페이지 틀만 있다. 왼쪽 메뉴 9개(시안 승인 이름): AI Market Home · All Products · AI Robots · AI Software · AI Hardware · Compare · Buying Guide · Featured · Inquiry (한국어: AI 마켓 홈 · 전체 제품 · AI 로봇 · AI 소프트웨어 · AI 하드웨어 · 제품 비교 · 구매 가이드 · 추천 제품 · 문의·상담).
- 9개 항목 전부 `section: null` = 글자 없는 빈 카드 틀. 데이터 소스 0, DB 테이블 0, 어드민 화면 0.
- 틀은 `watch_as_home` 뒤(꺼짐=404), `/ko/market` 포함. 언어 층(영어 정본 + `ko`)과 배너 키 `banner_market`(아직 행 없음)은 이미 연결 가능.
- 이 틀에 데이터를 꽂는 방식은 이미 정해져 있다: 항목에 `section`(데이터 소스 id)을 주면 되고 컴포넌트는 안 바뀐다. 단 현재 `SectionId`는 **영상 콘텐츠 종류**(film·drama·cf·music·news…)용이다. Market은 영상이 아니라 제품이라 **소스 종류를 하나 더 만들어야 한다**(카드 모양 `HomeCard`도 제품용 필드가 필요한지 확인 필요).

## 2. 먼저 답이 필요한 4가지 (EOD 5절 그대로) -- 내 가정과 답에 따라 갈리는 것

| # | 질문 | 누구에게 | 내가 지금 가정하는 것(틀렸으면 정정 요청) | 답이 바꾸는 것 |
|---|---|---|---|---|
| Q1 | **Market이 파는 것의 출처는?** 우리가 직접 파는가, 외부 AI 제품 판매사 상품을 소개·연결만 하는가, 둘 다인가 | TK님(사업), 제니2 | 가정 **없음**. 모르는 것을 일반 마켓플레이스 패턴으로 채우지 않는다(사업 본질 확인 원칙) | 결제·재고·주문 테이블 필요 여부(직접 판매면 Stripe·세금·배송까지 별도 설계), 아니면 "소개 + 외부 링크"만으로 끝나는 가벼운 구조 |

| Q3 | **Compare / Buying Guide의 데이터 구조** (제품 속성 비교표? 편집 기사? 둘 다?) | 제니2(기획), TK님 | 가정 없음. 선택지는 4절 | 제품 테이블에 속성 컬럼을 두는가, 카테고리별 속성 정의를 두는가, 가이드는 별도 글 형식인가 |
| Q4 | **실제 회사 이름·로고 사용 범위** | TK님(+법무 판단은 레포 밖) | 시안의 실제 회사 이름·로고는 **사용 금지**(10-11 확정). 제품 소개에 상표를 쓰는 건 별개 문제라 확정된 적 없음 | 제품명·판매사명·로고 이미지 필드를 둘지, 둔다면 누가 입력·검수하는지 |

## 4. 구조 선택지 (아직 고르지 않음)

**A. 제품 소스**
- A1 *(가벼움)* `market_products` 한 테이블: slug, 카테고리, 상태(draft/published), 제목·설명(영어 정본), 대표 이미지(R2, 영상 썸네일과 같은 role 방식 가능 여부 확인), 외부 링크, featured 순서. 번역은 기존 `pickTranslation` 자리(영어 정본 + 번역 층)를 따른다.
- A2 *(직접 판매 시)* A1 + 가격·재고·주문·결제. **Q1이 "직접 판매"일 때만.** 크기가 한 단계 다르므로 별도 설계 문서로 분리.

**B. 비교(Compare)**
- B1 제품 행에 `specs`(JSON) 한 컬럼: 빠르지만 카테고리마다 필드가 달라 비교표 헤더를 코드가 추측해야 함.
- B2 카테고리별 속성 정의 테이블 + 제품별 값 테이블: 비교표가 정의에서 자동으로 나옴, 대신 어드민 입력 화면이 커짐.
- 내 의견(약한 추천): 제품 수가 적은 초기에는 B1로 시작하고 속성 정의는 B2로 넘어갈 때 이관. 단 **제품이 몇 개로 시작하는지 모르므로** 이것도 Q1·제니2 답 후에 확정.

**C. 문의(Inquiry)** -- Q2 답에 따라
- C1 메일 링크: 코드 0. 반송은 `info@`로만 수신(10-08 TK 결정과 일치).
- C2 폼: `market_inquiries` 테이블(이름·이메일·메시지·대상 제품 id 선택·시각·상태), 서버 전용 쓰기(`createSupabaseAdmin`), 익명 읽기 차단, IP·이메일 속도 제한, 어드민 목록 + 새 문의 알림 메일(`lib/email/messages.ts` 표준 문구 방식).

**D. 공개 게이트**: 영상은 `lib/content-public.ts`의 공개 판정(공개 문)을 통과해야만 나온다. 제품도 **같은 원칙의 단일 문**(상태 published + 어드민이 올린 것만, 필요한 컬럼만 select)을 먼저 만들고, 페이지·카드는 그 문만 통해 읽는다. 새 읽기 경로가 문을 우회하지 못하게 소스 가드 테스트를 건다.

## 5. 작업 순서 안

0. **Q1~Q4 답 수집**(이 문서가 질문서). 답 전에는 아래 어느 것도 시작하지 않는다.
1. 설계 확정 문서 한 장: 선택한 A·B·C, 테이블 정의, 접근 권한표(anon/authenticated/service_role별).
2. 마이그레이션 SQL (TK님 Run, 블록 1개 = 쿼리 1개, 채팅 본문 전달, ASCII만, 한글 저장값은 한글 그대로). 새 테이블은 명시적 REVOKE + GRANT + RLS, 공개 읽기는 view(`seasons_public` 방식), 함수는 `aclexplode`로 ACL 되읽기. **마이그레이션 Run 확인 후에 코드 푸시.**
3. 공개 문(읽기 함수) + 단위 테스트 + 훼손 시험(문을 우회하는 읽기 추가 / draft가 새어 나옴 / 컬럼 과다 select가 각각 빨개져야 함, 대조군 포함).
4. `SectionId`에 제품 소스 추가, `site-nav`의 Market 항목들에 `section` 연결, 카드 모양 결정(영상 카드 재사용 vs 제품 카드), 영어 카탈로그(문구는 제니3 확정본).
5. 어드민 입력 화면(제품 CRUD, featured 순서, 상태 전환). 어드민은 영어 화면 규칙을 따른다.
6. (C2 선택 시) 문의 폼 + 어드민 목록 + 알림 메일 + 속도 제한 시험(IP 위조 헤더 대조군 포함).
7. 배너 `banner_market` 파일·키 행(제니2 파일 → R2 → TK님 SQL).
8. 라이브 스모크: 점검표 방식(`watch_as_home` 꺼짐=404 유지, 켠 뒤 200, 배포 후 새 deploymentId 확인).

## 6. 지키는 규칙 (이미 확정된 것들)

- 운영 파라미터 하드코딩 금지(featured 순서, 페이지 크기, 카테고리 목록 노출 여부는 DB/설정에서).
- "Coming Soon" 글자 금지. 데이터 없는 항목은 빈 틀.
- 새 페이지는 계속 `watch_as_home` 뒤. 이 작업이 그 스위치 의미를 바꾸지 않는다.
- 서버 쓰기는 `createSupabaseAdmin`. 클라이언트에서 직접 쓰기 없음.
- 언어: 영어 정본 + 번역 층. 한 화면에 한 언어. 번역 없으면 영어로 폴백.
- 비밀값·서비스 키를 읽지 않는다. 배포·스위치 변경·커밋은 TK님 지시가 있을 때만.

## 7. 이 계획이 모르는 것 (정직하게)

- Market 사업 모델 자체(Q1). 시안 이름 9개 말고는 Market이 무엇을 파는지 확인된 문서가 레포에 없다.
- 영상 콘텐츠 시스템(`content_*` 테이블)을 제품·가이드에 재사용할 수 있는지는 **코드·스키마를 아직 대조하지 않았다.** 설계 확정 문서 단계에서 라이브 스키마를 `pg_get_*` 등으로 실측한다(레포 파일만으로 부재·존재를 단정하지 않는다).
- 제품 수 규모, 가격 표기 여부, 다국가 판매 여부 -- 전부 Q1에 딸린 미지수.
- 일정은 적지 않는다. 진행은 "답 수집 → 설계 확정 → SQL Run → 문 → 화면" 순서의 검증 가능한 단계로만 보고한다.
