## 1. A의 렌더 리스 구현 — 읽었다. 기전은 이식되고, ★정책은 안 된다

### A가 한 것 (`worker 9a490a3` + `lib/studio.ts:2156~2243`)

| 요소 | 내용 |
|---|---|
| 스탬프 | 클레임 시 `claimed_at` |
| 폴백 | `row.claimed_at ?? row.updated_at` — 배포 이전 행도 판정 가능 |
| 임계 | `RENDER_LEASE_STALE_MS` 기본 30분 = **`RENDER_TIMEOUT_MS`(15분)의 2배** |
| 재큐잉 | `rendering`/`uploading` → `queued`, `claimed_at=null`, **관측 status로 CAS** |
| attempts | 리스 재큐잉에서 **건드리지 않음** |
| 위치 | **앱** season-tick(시간당). 새 Vercel cron 안 만듦(plan limit 3) |

### ★임계를 어떻게 구했는가가 핵심이다

A는 **먼저** ffmpeg 호출에 타임아웃을 넣고(`0350b51`), **그 다음** 리스 임계를 그 2배로
잡았다. 논리: **워커 자신의 타임아웃이 먼저 터져서 행을 `failed`로 만든다. 리스는
프로세스가 청소도 못 하고 죽었을 때만 발동한다.**

★**이 순서를 그대로 반복해야 한다** — 임계는 호출 상한에서 유도되지, 감으로 정하는 게
아니다(규율 2).

★**그런데 나머지 두 레인엔 호출 상한이 없다:**
- 클립: `fal.subscribe`에 **월클럭 바운드가 없다**. `withRetry`는 에러 시 재시도할 뿐,
  **멈춰 있는 subscribe는 영원히 기다린다** (`src/fal.ts:48~67`).
- 음악: 내 경계가 `generate()`를 "내부적으로 폴링해도 된다"로 정의했고 **상한을 안 걸었다.**
  ★내 설계 누락이다.

→ ★**선행 작업 = 두 레인에 호출 타임아웃 먼저.** 그게 없으면 임계가 근거 없는 숫자다.

### ★★기전은 이식되고 정책은 이식되면 안 된다 — 이게 답의 핵심

| | 재큐잉 1회 비용 | 무한 재큐잉 |
|---|---|---|
| 렌더 | **CPU만** (createRender는 크레딧 미차감) | 감당 가능 |
| 클립 | **fal 과금 1회** | ★불가 |
| 음악 | **벤더 과금 1회** | ★불가 |

A의 리스 분기는 **횟수 제한이 없다**(재큐잉 → 재클레임 → 또 죽음 → 또 재큐잉).
`attempts`는 클레임 때 증가하지만 **읽는 코드가 어디에도 없다**(`grep` 전수 확인).
A의 `failed` 분기는 `REQUEUED_STATE`로 1회 제한이 있지만 **리스 분기엔 없다.**

★**렌더에겐 옳은 선택이다** — CPU만 드니 계속 시도하는 게 낫다.
★**클립·음악엔 그대로 쓸 수 없다** — 매 재큐잉이 벤더 청구서다.

**그래서 이식 결론:**
- ✅ `claimed_at` 스탬프 + `coalesce` 폴백 + 관측 status CAS → **그대로 쓴다**
- ✅ 임계 = 호출 타임아웃 × 2 → **그대로 쓴다** (단 타임아웃부터 만들어야 함)
- ❌ 무한 재큐잉 → **못 쓴다. `attempts` 상한 + 종착지 = 환불**
- ❌ `.not('submit_intent_at','is',null)` 필터 → 못 쓴다 (아래 1-b)

### 1-b. ★A의 스위프 범위에 대한 관찰 (A 소관, 보고만)

`sweepAsyncSubmissions`는 **제출 intent가 있는 렌더만** 훑는다
(`lib/studio.ts:2178`). **제출 안 한 렌더**(참가자가 편집 중 돌린 것)가 정지하면
회수되지 않는다. 돈은 안 걸려 있으니 발사 블로커는 아니다. A 판단 사항.

## 3. ★이중 생성·이중 과금 — 무엇이 구조적으로 불가능하고, 무엇이 남는가

### 3-a. 참가자 이중 과금 = ★구조적으로 불가능

과금은 **enqueue 시점 1회**다(`createMusicGeneration` 6단계 / 클립도 동일).
클레임·재큐잉·재생성은 **크레딧을 건드리지 않는다.** 몇 번을 재시도하든 참가자
원장에는 charge 행이 하나뿐이다. → **방어가 필요 없다. 이미 그렇다.**

### 3-b. 이중 환불 = ★이미 막혀 있다

음악(`refundMusicJob`)·클립(`refundFailedJob`) 둘 다 **선행 refund 행 조회 후 삽입**한다.
멱등. → 추가 조치 없음.

### 3-c. ★벤더 이중 과금 = 남는다. 제거 불가, **상한만 가능**

계약(`MusicProvider.generate`)이 폴링을 캡슐화하므로 **진행 중인 벤더 요청을
재개할 방법이 없다.** 죽은 워커가 벤더를 이미 호출했는지 알 수 없다.

→ **선택지는 둘뿐:**

| | 결과 |
|---|---|
| 재큐잉 | 참가자는 트랙을 받는다. **우리가 벤더에 두 번 낼 수 있다** |
| 실패+환불 | 우리는 한 번만 낸다. 참가자는 **시간을 잃는다**(72h 창에서 비쌀 수 있음) |

★**권고 = `attempts` 기반 하이브리드.** A의 "1회 재시도" 원칙과 같은 모양이다:

```
attempts < 2  → 재큐잉   (벤더 초과분 최대 1회로 상한)
attempts >= 2 → 실패+환불 (종착)
```

근거: 참가자는 환불로 **완전히 원상복구된다** — 크레딧이 돌아오고,
`countMusicGenerationsForRound`가 `queued/generating/ready`만 세므로 `failed`는
**캡 슬롯도 반납한다**(`lib/music-gen.ts:157`). 즉 재시도는 **참가자의 선택**이 되고,
자동 재큐잉은 **우리 돈을 참가자 동의 없이** 쓰는 쪽이다. 무상 0원 정책과 정합.
그래도 첫 1회는 자동으로 봐주는 게 마감 앞 참가자에게 맞다.

### 3-d. ★★좀비 쓰기 = 제거 가능. 그리고 이게 진짜 위험이다

**시나리오**: 워커 A가 클레임 → 멈춤 → 스위퍼가 재큐잉 → 워커 B가 재클레임·완료·서명 →
**그 뒤 워커 A가 깨어나서 자기 결과를 쓴다.**

현재 내 finalize CAS는 `.in('status', ['queued','generating'])`뿐이다. 재클레임된 행은
그 사이 `ready`이므로... **B가 먼저 끝냈으면 A의 쓰기는 튕긴다.** 그런데 **A가
`generating` 중에 깨어나면 통과한다** — B가 아직 진행 중일 때.

★**더 나쁜 건 R2다.** 키가 `music/{season}/{user}/{assetId}.{ext}`로 **assetId 결정적**이라,
좀비가 **같은 키를 덮어쓴다.** 행은 B의 `contentHash`로 서명돼 있는데 오브젝트는 A의
바이트 → ★**v1m 검증이 렌더 시점에 깨진다**(`verifyMusicAssetBind`가 재해시로 대조).
참가자 베드가 조용히 망가진다.

**해법 2개, 둘 다 필요:**

1. **`claim_token`** — 클레임 시 uuid 스탬프, finalize를 `.eq('claim_token', mine)`로 CAS.
   좀비의 DB 쓰기가 **거부된다.**
2. **R2 키에 토큰 포함** — `music/{season}/{user}/{assetId}-{token8}.{ext}`.
   각 시도가 **다른 오브젝트**를 쓰므로 덮어쓰기가 불가능하다. 진 쪽은 고아 오브젝트로
   남는다(무해, 일회성 정리 대상).

★1번만으로는 부족하다 — 행은 지켜도 **바이트가 안 지켜진다.** 두 개가 같이 가야 한다.
★**렌더도 같은 모양이다**(v1sc 서명 + 결정적 렌더 키). A에게 보고 대상.

### 3-e. 요약표

| 위험 | 상태 |
|---|---|
| 참가자 이중 과금 | ✅ 구조적으로 불가능 (enqueue 1회 과금) |
| 이중 환불 | ✅ 이미 멱등 |
| 벤더 이중 과금 | ⚠️ **제거 불가. `attempts<2`로 최대 1회 초과로 상한** |
| 좀비 DB 쓰기 | ✅ `claim_token` CAS로 제거 |
| 좀비 R2 덮어쓰기 → **서명 파손** | ✅ 키에 토큰 포함으로 제거 |
| 고아 R2 오브젝트 | ⚠️ 남음. 무해, 정리 대상 |

## 4. 임계값 — 전부 유도, 지어낸 상수 0

| 상황 | 임계 | 유도 |
|---|---|---|
| 렌더 `rendering` 정지 | 30분 | `RENDER_TIMEOUT_MS`(15분) × 2 — **A가 이미 함** |
| 클립 `generating` 정지 | ★**호출 타임아웃 × 2** | ★**타임아웃이 아직 없다. 먼저 만들어야 함** |
| 음악 `generating` 정지 | ★**호출 타임아웃 × 2** | ★**동일. 경계에 상한을 안 걸었다 — 내 누락** |
| 음악/클립 `queued` 정지 | ★**라운드 경계** | 아래 |

### ★`queued` 정지는 타이머가 아니라 라운드로 정의한다

"큐에서 얼마나 기다리면 환불인가"는 처리 시간에서 유도할 수 없다 — 정책 값이다.
★**지어내지 말고 시즌에서 읽는다: 라운드가 닫히면 그 잡은 쓸 수 없으므로, 그 시점에
환불한다.** `seasons`의 마감 컬럼에서 나오지 상수가 아니다(하드코딩 금지).

이 하나가 **세 구멍을 동시에 닫는다:**
- 영구 rate-limit으로 무한 대기 (직전 보고 구멍 3)
- DB 스위치 ON인데 배포에 레인 없음 (부팅 가드가 못 잡는 가동 중 전환)
- 워커가 장기 다운 — ★**한 달 다운이 실제로 있었다**

## 5. 스위퍼 위치 — ★앱(season-tick). 워커 아님

워커에 두면 cron 제약도 없고 A 파일도 안 건드린다. **그런데 결정적 반례가 있다:**

★**워커가 죽어 있을 때 환불이 일어나야 한다.** 워커 안의 스위퍼는 정확히 회수해야 할
그 상황에서 같이 죽어 있다. 재큐잉은 워커가 없으면 의미 없지만 **환불은 의미 있다** —
그게 돈이다. 워커 한 달 다운 때 갇혔을 참가자 크레딧이 정확히 이 경우다.

→ **앱 season-tick.** A의 `sweepAsyncSubmissions`와 같은 자리.

★**접촉면**: `app/api/cron/season-tick/route.ts`는 **A 소유**다. 필요한 건 **한 줄**
(`sweepStudioLeases()` 호출). 본체는 내 파일(`lib/studio-lease.ts`)에 둔다.
**A 확인 후 넣는다.**

## 7. 판정 요망 3건

1. **`attempts < 2` 재큐잉 1회 후 환불** — 벤더 초과분 최대 1회를 받아들이는 것. 대안은
   무조건 즉시 환불(우리 돈 0 초과, 참가자 시간 손실).
2. **`generation_jobs.claimed_at` 추가 여부** — 기능상 불필요(`worker_started_at`이 대체).
   스위퍼 컬럼명 통일이 유일한 이득.
3. **`render_jobs.claim_token`** — A 소관. 렌더도 같은 서명 파손 위험이 있다는 것만 보고.

★그리고 A에게 전달할 관찰 2건: 리스 재큐잉 무한(렌더는 무해) / 스위프가 제출 intent
있는 행만 훑음.
