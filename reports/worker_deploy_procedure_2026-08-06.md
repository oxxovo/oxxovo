## 0. ★먼저: 두 가지를 정정한다

### 0-1. `watch_hidden` 은 리허설 추출 실패를 **안 고친다**

본부 순서가 "①watch_hidden 7행 → ②배포 → ③리허설" 이었고, 근거가
"그게 리허설이 매번 추출 실패하는 원인" 이었다. **그 부분이 틀렸다.**

실측: `watch_hidden` / `watch_hidden_at` / `watch_hidden_reason` 세 컬럼은
DB 에 있고 **앱만** 읽는다 — `app/admin/watch-videos/page.tsx`(어드민 숨김 목록),
`app/watch/actions.ts`(숨김 토글), `e2e/run.mjs`(공개 판정).
**채점 워커는 이 컬럼을 한 번도 읽지 않는다** (`oxxovo-scoring/src` 전체 0건).

워커의 후보 선정은 `status` + `영상 URL not null` 이다. 그래서 7행을 숨겨도
워커는 **여전히 집어서 추출을 시도하고 404 로 실패**한다. 숨김은 **Watch 가시성**의
답이지 리허설의 답이 아니다.

**그럼 리허설은 어떻게 되나**: 막히지는 않는다. 7건이 재시도 소진 → `failed` 로
떨어지고, `countUnfinished` 는 소진분을 "끝난 것" 으로 세므로 확정까지 간다.
★단 **결과가 7건 오염된 채로 나온다.** 그리고 새 `countUndeliverable` 은
**URL 이 null 인 행**을 세는데 이 7행은 URL 이 있으므로(죽었을 뿐) 보류도 안 걸린다.

**제안**: 두 가지를 분리한다.
- `watch_hidden = true` — 본부 지시대로 진행. Watch 에서 안 보이게 하는 것이 목적.
- **리허설 오염 제거는 별도** — 테스트 데이터 문제이므로 `scripts/rehearsal-*.mjs`
  가 제외하는 쪽이 맞다. 워커가 `watch_hidden` 을 보게 만드는 것은 **프로덕션 채점
  정책 변경**이다("숨겨진 작품은 채점 안 한다"). 숨김은 모더레이션 행위이지 기권이
  아니므로, 그 정책은 별도 승인 사안이다. **이 배포에 끼워 넣지 않는다.**

→ **순서에서 ① 을 배포의 선행 조건에서 뺀다.** 병렬로 해도 되고 뒤에 해도 된다.

### 0-2. 배포 확인 신호 — 본부가 지목한 문구는 **11/4 전에는 안 바뀐다**

새 게이트의 검사 순서는 `close NULL → close 미래 → 버퍼 → status` 다.
지금은 `close(11/4)` 가 미래라 **2번에서 먼저 끊긴다.** 버퍼 게이트는 도달조차
안 하므로, 차단 메시지는 배포 전후가 **글자 그대로 같다.**

★**대신 확실한 신호가 하나 있다** — 시작 시 찍는 설정 로그의 문구가 바뀐다:

```
현행 배포본   SEASON_REQUIRED_STATUS=(없음 — application_close_at 단독 게이트)
배포 후       SEASON_REQUIRED_STATUS=(없음 — 마감 시각 단독 게이트)
```

`src/batch.ts:390`. **한 줄이고, 첫 크론 실행에서 바로 보이고, 11/4 를 안 기다린다.**
이것이 배포 확인 신호다.

## 1. ① 머지 방식 — **PR + `--no-ff` 머지 커밋**

실측: `git rev-list --left-right --count origin/main...origin/feat/main-round-worker`
→ **`0  26`**. 브랜치가 main 보다 **뒤처진 게 없다** = 충돌 없음, fast-forward 가능.

★**그래도 fast-forward 를 쓰지 않는다.** 이유는 되돌리기다.
FF 로 붙이면 26개 커밋이 main 에 펼쳐지고, 되돌리려면 26개를 되돌려야 한다.
`--no-ff` 는 **머지 커밋 하나**를 남기고, 그 하나만 `git revert -m 1` 하면
26커밋 전체가 한 번에 빠진다. **되돌리기 손잡이가 하나여야 한다.**

리뷰 단위: 26커밋이지만 **주제가 7개**이고 각각 테스트를 달고 있다
(Defect1 · 버퍼게이트 · 아암D · 스냅샷고정 · 지문 · 배점 · ■6).
PR 본문에 그 7개를 표로 적어 리뷰 단위를 만든다 — 커밋 26개를 순서대로 읽게 하지 않는다.

빌드 확인 (실측, Dockerfile 과 동일 조건):
`src` + `tsconfig.json` + `package*.json` 만 있는 디렉터리에서 `tsc` → **exit 0,
`dist/batch.js` 생성.** tsconfig 의 `include` 가 `src/**/*` 라 루트 하니스(`_test_*.ts`)는
이미지에 안 들어가고 빌드에도 안 걸린다.

## 2. ② ★되돌리기 경로 — **확인 전에는 배포하지 않는다**

되돌릴 수 없는 배포는 하지 않는다는 원칙에 동의한다. 경로는 둘이고, **최소 하나가
확인돼야** 진행한다.

| | 경로 | 누가 확인 | 상태 |
|---|---|---|---|
| A | Railway **Deployments → 이전 배포 Rollback** | **TK만 가능**(대시보드) | ★미확인 |
| B | `git revert -m 1 <머지커밋>` → push → 재배포 | 나 | 구조상 확실 |

★**나는 A 를 확인할 수 없다.** Railway 대시보드 접근이 없다. TK 확인 필요:
`Deployments` 목록에서 **직전 성공 배포에 Rollback(또는 Redeploy) 버튼이 있는가.**

★그리고 A 에는 함정이 있다: **Rollback 은 이미지를 되돌리지 브랜치를 되돌리지
않는다.** Railway 가 main 을 보고 auto-deploy 중이라면, 롤백 후 누가 main 에
아무거나 push 하는 순간 새 코드가 다시 배포된다. **그래서 진짜 되돌리기는 B 다.**
A 는 "빨리 멈추는" 수단이고 B 는 "되돌리는" 수단이다 — 둘의 역할이 다르다.

★**B 는 A 없이도 성립한다.** 그래서 A 가 없더라도 배포 가능하다는 것이 내 판단이지만,
**"안 되면 배포하지 않는다" 는 본부 기준이므로 A 확인 결과를 받고 진행한다.**

### ★그리고 먼저 답해야 할 것 — Railway 연결 브랜치

`railway.json` 에는 **브랜치가 없다**(빌더/시작명령만). 연결 브랜치는 Railway
서비스 설정에만 있고 **레포에서 알 수 없다.** TK 확인 필요:
**Settings → Source → 연결 브랜치.**

내가 좁힐 수 있는 것:
- `origin/main` = `9516ae9` (**2026-06-02**), `origin/feat/main-round-worker` = 오늘.
- 본부가 본 "11일 전 커밋" 은 **둘 중 어느 브랜치 tip 과도 다르다.**
  → 환경변수 변경으로 **핀된 기존 배포를 재배포**한 것으로 보인다(브랜치 tip 을
  새로 당겨온 것이 아니라).
- ★어느 쪽이든 **새 코드는 확실히 미배포다.** main 에 없기 때문이다(+26, +9,400줄).

## 3. ③ TK님이 누르실 것 — 단계별

**사전(TK, 대시보드 확인 2건)**
1. Railway → **Settings → Source** → 연결 브랜치 확인 후 알려주기
2. Railway → **Deployments** → 직전 배포에 **Rollback 버튼 유무** 확인 후 알려주기

**여기서 멈춘다.** 위 둘을 받고 아래를 확정한다.

**배포(둘 다 확인된 뒤)**
3. 지수 본체가 PR 생성 (`feat/main-round-worker` → `main`, 본문에 주제 7개 표)
4. TK → GitHub PR → **Merge pull request** → ★**"Create a merge commit"** 선택
   (Squash·Rebase 금지 — 되돌리기 손잡이가 하나여야 한다)
5. Railway 가 main 을 보고 auto-deploy 중이면 자동 시작. 아니면 **Deploy** 수동
6. 빌드 로그에서 `dist/batch.js` 생성 확인

**확인(다음 크론 실행, 최대 1시간)**
7. 로그 첫 줄들에서 **`SEASON_REQUIRED_STATUS=(없음 — 마감 시각 단독 게이트)`** 확인
   → **이 문구가 배포 확인 신호다.** 옛 문구(`application_close_at 단독 게이트`)면
   배포가 안 붙은 것이다.
8. 이어서 `⏸ 채점 게이트 차단 — SKIP: ... 아직 신청 마감 전` / `Batch skipped` 확인
   → **이 문구는 배포 전후가 같다.** 정상이다(11/4 전이라 close 검사에서 먼저 끊긴다).

**되돌려야 하면**
9. 즉시 멈춤: Railway **Rollback**(가능하면)
10. 진짜 되돌리기: `git revert -m 1 <머지커밋>` → push → 재배포

## 4. ④ 배포 후 즉시 볼 것 — 정상 판정표

| 로그 | 정상 | 이상 시 |
|---|---|---|
| `SEASON_REQUIRED_STATUS=(없음 — **마감 시각** 단독 게이트)` | 배포 붙음 | 옛 문구면 미배포 |
| `BATCH_SIZE` · `SEASON_ID=season_0` | 이전과 동일 | 값이 바뀌었으면 env 사고 |
| `⏸ 채점 게이트 차단 — SKIP: application_close_at(2026-11-04T08:00:00Z) 이 미래` | **동일** | 이 문구가 사라지고 채점이 시작되면 **즉시 롤백**(11/4 전인데 게이트가 열린 것) |
| `=== Batch skipped (채점 시점 아님) ===` | 동일 | 위와 같음 |
| 에러/스택트레이스 | **없어야** | 있으면 롤백 |

★**"아무것도 안 달라 보이는 것" 이 정상이다.** 달라져야 하는 것은 설정 로그 한 줄뿐이다.
채점이 시작되면 그게 이상 신호다.

## 5. 배포 후 — 리허설 (검증)

리허설로 **배포한 물건**을 시험한다 — 그때 비로소 성립하는 말이다.

리허설 전 정리(위 0-1): `season_test` 의 404 자산 7건을 하니스에서 제외.
안 하면 결과에 7건 실패가 섞여 "버퍼 게이트가 제대로 도는가" 를 읽기 어려워진다.

리허설에서 확인할 것 — 이번 배포로 **새로 생긴 동작**만:
1. `buffer-done` 전에는 **예선 워커가 안 돈다**(버퍼 게이트 (a))
