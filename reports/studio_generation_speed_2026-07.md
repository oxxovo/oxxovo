# Studio 생성 속도 전수 실측 (2026-07-16 저녁 PT, 지수2)

TK 승인 $5.75. 11종(경기 7+드래프트 4) 최소길이 각 1편을 fal 큐 API로 **동시 발사**,
IN_QUEUE -> IN_PROGRESS -> COMPLETED 전이를 2초 해상도로 기록 (`oxxovo-studio/_speed_probe.mjs`).

## 핵심 발견 3개

1. **큐 대기 = 전 모델 2초.** 11개 동시 발사가 즉시 전원 IN_PROGRESS.
   -> 관측 동시성 **11/11**, fal 계정 상한은 11 이상 (정확한 한도는 대시보드 확인 필요).
2. **어제의 "59분"은 모델 고유 속도가 아니라 fal 혼잡 변동이었다.**
   같은 veo3.1 4s가 어제 3,549초 -> 오늘 **185초(3.1분)**. veo31-lite는 반대로
   어제 47초(무음)~299초 -> 오늘 403초. **모델별 고정 속도표는 성립하지 않고,
   시간대 혼잡이 지배 변수.**
3. **처리 시간(순수 생성)은 대체로 1~7분 범위.** 우리 쪽(워커 폴링/큐) 병목 0.

## Q4 -- 72시간 30회+조합 성립 계산

**개인 체감 (1인 기준)**: 평균 ~3분/편 -> 30회 연속 생성 = **~1.5시간**, 혼잡 최악
(59분/편)이어도 병렬 발사하면 대기 중첩 -> 개인 차원 성립. **단 혼잡 시 반복
(피드백 루프) 지연이 창작을 죽임** -> 빠른 드래프트(터보 78s)가 해답 (이미 구현).

**플랫폼 용량 (500명 시즌0)**: 500 x 30회 x 2(드래프트캡 포함 최대) = 최대 3만 편/72h
= 평균 417/h, 피크 x3 = ~1,250/h. 편당 ~3분 -> **필요 동시 슬롯 = 피크 ~60**.
- 현재 워커 `WORKER_CONCURRENCY=10` -> **10 슬롯 = 200/h. 여기가 진짜 병목.**
- fal 상한: 관측 >=11, 실제 한도 미확인. **60 슬롯 확보 가능한지가 발사 게이트**
  ([[project_studio_season0_full_load]]의 "유일 관문=fal 동시성"과 일치).
- compose 렌더: `RENDER_CONCURRENCY=2` (ffmpeg CPU) -- 마감 직전 500 최종렌더 몰림
  시나리오는 별도 계산 필요 (렌더 1편 ~수십 초 x 500 / 2 lanes = 수 시간. 증설 대상).

## Q6 -- 느린 모델 처리안 (권고, 결정은 TK+고문)

**제외 비권고.** 오늘 veo3.1이 3분인 것처럼 "느린 모델"이 고정이 아니라 혼잡 변동.
권고 조합:
1. **실측 기반 예상 소요 표시** (아래 UX#2) -- 정적 라벨이 아니라 최근 실측 롤링
   중앙값 + "혼잡 시 크게 늘 수 있음" 문구. 하드코딩 금지 원칙과도 부합.
2. **마감 임박 경고**: 마감 N시간 전부터 변동 큰 모델(veo 계열)에 경고 배지.
3. 극단 혼잡(예: 편당 >15분 관측)이 지속되면 그때 임시 비활성 (active=false 데이터
   스위치, 코드 0) -- 상시 제외보다 유연.

## UX 2건 구현안

1. **백그라운드 생성 + 완료 알림**: 생성은 이미 백그라운드(페이지 떠나도 워커 진행,
   재접속 시 반영). 추가 = 탭 이탈 시 브라우저 알림(Web Notifications, 폴링이 ready
   감지 시 발사) + 탭 타이틀 뱃지. 서버 무변, **~0.5일**. (이메일 알림은 옵트인 필요
   +스팸 위험 -> 후순위 제안)
2. **모델별 예상 소요 표시**: generation_jobs 최근 완료분 롤링 중앙값(모델별 최근
   20건)을 loadStudioState에 합류 -> 모델 옵션/생성 중 카드에 "보통 ~N분" 표시.
   표본 부족 모델은 오늘 전수표를 시드로. **~0.5일**.
