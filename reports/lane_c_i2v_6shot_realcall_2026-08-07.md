## 4. ★종횡비 -- 카탈로그의 `aspect_ratio: '16:9'`가 무력하다

출력이 **1244x1664 = 3:4 세로**다. 카탈로그
`model_catalog.metadata.input_params`는 `{"cfg_scale":0.5,"shot_type":"customize",
"aspect_ratio":"16:9","generate_audio":true}`이고 워커는 이걸 fal 입력에 그대로
넣는다(`worker.ts:519`). **그런데 16:9가 안 나왔다.**

출처를 실측했다:

| | 크기 | 비율 |
|---|---|---|
| start_image (부모 정면, `1e80b303`) | 1792 x 2400 | 0.7467 (3:4) |
| ⑪B 출력 (6샷 12s) | 1244 x 1664 | 0.7476 (3:4) |
| **⑪A 출력 (1샷 5s, 어제)** | **1244 x 1664** | 0.7476 (3:4) |

→ **Kling i2v는 `aspect_ratio`를 무시하고 start_image의 비율을 따른다.** 독립된 두 번의
생성(⑪A 1샷 / ⑪B 6샷)이 같은 값을 냈으므로 이번 잡의 특이현상이 아니다.

왜 중요한가:
- 참가자 배우 시트가 `nano-banana-pro`로 세로로 나오면 **모든 i2v 클립이 세로**다.
- Studio 종횡비 작업(레터박스 기본 + 클립별 크롭 토글)에서 16:9 캔버스에 3:4 클립을
  넣으면 좌우 레터박스가 크게 생긴다. **"16:9로 시켰으니 16:9로 온다"는 전제가 깨져 있다.**
- 카탈로그에 값이 있고 효과가 없으면 그건 **설명할 수 없는 상수**다. 지우거나(데이터
  변경 = DB 쓰기, 본체) 무력함을 명시해야 한다.

★**단정하지 않는 것**: t2i 쪽에서 배우 시트를 16:9로 만들면 i2v도 16:9로 나오는가 --
그건 안 재봤다. 재려면 이미지 1장($0.045~0.15) + i2v 1회가 더 든다. **비용 발생이라
승인 없이 안 한다.**

## 5. CryptoBind 재계산 -- 바이트에서 다시 계산했다

행을 믿지 않고, 내려받은 파일에서 두 단계를 모두 재계산했다.

| 검사 | 결과 |
|---|---|
| parent bundle (부모 3장의 v1i 서명, 정렬 후 sha256) | **MATCH** `62532c4352b1355d…` |
| **v1v 생성 서명** (pid·tid·jobId·생성시각·모델·12s·bundle) | **MATCH** `4436f964ee91186a…` |
| **콘텐츠 해시** (내가 내려받은 16,751,463 바이트의 sha256) | **MATCH** `7c294d312a34b15f…` |
| **v1c 콘텐츠 서명** | **MATCH** `35695d5a2666f485…` |
| 네거티브 컨트롤 (duration을 12→13으로만 바꿔 서명) | **REFUSED** |

★콘텐츠 해시가 맞는다는 것은 **내가 ffprobe한 바이트가 워커가 서명한 바로 그 바이트**라는
뜻이다. 그래서 3절·4절의 측정이 "이 잡의 산출물"에 대한 진술이 된다.
★네거티브 컨트롤을 같이 돌린 이유: 전부 MATCH만 찍는 검사는 **아무것도 거부할 수 없어도
통과한다**. 한 필드를 1 바꿨을 때 거부되는 것을 같이 보여야 MATCH가 의미를 갖는다.

## 6. 지출 전에 비용 0으로 막은 것 2건

★**(a) "2초"가 스키마 유효한지 -- 레포 주석과 어긋났다.** 워커
`src/fal.ts:113`은 `'string' kling-v3 ('3'..'15')`라고 적어 두었다. 지시는 2초였다.
fal OpenAPI 실스키마를 무료로 조회한 결과:

```
multi_prompt[].duration  enum ["1","2","3",…,"15"]  default "5"
top-level    duration    enum ["3","4","5",…,"15"]  default "5"
```

→ **두 enum이 다르다.** `'3'..'15'`는 top-level 필드의 것이고, `multi_prompt` 항목은
`"1"`부터 받는다. 6x2s는 유효했고 실제로 통과했다. **레포 주석이 틀린 것은 아니지만
(top-level에 대해선 맞다) 그 문장만 보고 multi_prompt를 판단하면 틀린다.**

★**(b) 7/18 422의 원인은 샷 수가 아니었다.** `649ed536`(15s, 3샷x5s, `Unprocessable
Entity`, `actual_cost_usd=null`)과 44분 뒤 성공한 `dd118b00`(15s, **같은 3샷x5s**)의
입력을 나란히 놓으면 차이가 하나다:

```
649ed536  elements[0].reference_image_urls = []      → 422
dd118b00  elements[0].reference_image_urls = [2장]   → ready
```

fal 스키마도 `reference_image_urls`에 `"1-3 images supported"`라고 적어 둔다.
→ **참조 0장인 배우로 i2v를 보내면 부과→실패→환불 왕복이 확정**이다.
`createI2vGeneration`은 `refRows.map(...)`을 그대로 넣으므로 참조 0장이면 `[]`를 보낸다.
하니스는 그 경우 지출을 거부하도록 가드를 넣었다. **앱 쪽 서버 가드는 넣지 않았다** --
⑪ 활성화 대기 중이고 우선순위는 대표님 것이다. 아래로 올린다.

★부수: 422는 `actual_cost_usd=null`로 남았다 = **fal이 422에는 과금하지 않았다.**
그래서 "2초가 거부되면 얼마 손실인가"의 답은 **$0**이었다 -- 이 실험의 하방이 0이라는
사실이 지출 판단을 쉽게 만들었다.

### ★정정 -- "경합자가 하나였다"는 내가 틀렸다

처음 보고에서 나는 **"중복 워커 셋이 죽어 있는 것이 ⑪B 클레임 경합자가 1개였던
이유다"**라고 적었다. **틀렸다.** 배포 상태(`railway status --json`, 로그가 아니라 배포
레코드)와 타임스탬프를 다시 재서 나온 시간표:

```
08-02 19:53:19Z  just-vibrancy       render c215c6a5 -> zz_lane_a_hold READY
08-07 04:39:46Z  just-vibrancy       ★⑪A(88a8e86e) 클레임
08-07 04:48:01Z  just-vibrancy       ⑪A READY $0.8400  fal 019fda85
08-07 23:04:40Z  trustworthy-ench.   ⑪B(85fdc305) 클레임
08-07 23:20:54Z  trustworthy-ench.   ⑪B READY $2.0160  fal 019fde78
08-07 23:43:23Z  just-vibrancy       "Stopping Container"   ← ⑪B 종료보다 23분 뒤
```

두 가지가 뒤집힌다.

★**(a) ⑪A는 `just-vibrancy`가, ⑪B는 `trustworthy-enchantment`가 잡았다 -- 서로 다른
워커다.** ⑪A와 ⑪B 사이에 워커 편성이 바뀌었다. 제니2가 말한 어제의 near-miss에서
"클레임을 먼저 이긴 프로덕션 워커"의 정체가 `just-vibrancy`다.

★**(b) ⑪B 동안 `just-vibrancy`는 살아 있었다.** 정지 시각이 23:43:23Z이고 ⑪B는
23:20:54Z에 끝났다 -- **⑪B의 창 내내 살아 있는 워커가 최소 둘이었다.** 즉 경합자가
하나였던 게 아니라, **CAS 클레임 경쟁에서 한쪽이 이겼을 뿐**이다. 내 원래 문장은 결과
(클레임 1건)는 맞고 **이유를 틀리게 댔다.**

★**그래서 판정이 바뀌는 것**: 어제의 near-miss 조건은 ⑪B 때 **없어진 게 아니라 여전히
있었다.** 물리지 않은 이유는 편성이 비어서가 아니라 **살아 있던 두 워커 중 어느 쪽도 dev
모드가 아니었기 때문**이다(`DEV guard` 0 + `actual == estimated`). 지출 검증 결론 자체는
그대로 유효하다 -- 근거가 "경합자 없음"에서 "경합자는 있었고 둘 다 프로덕션 설정"으로
바뀐다.

크래시 사유는 둘 다 같다:

```
Error: WORKER_CONCURRENCY must be set explicitly in production (no default).
Render capacity is a deploy decision -- see the prelim load structure.
```

★**fail-closed 가드가 제 일을 했다** -- 그 변수 없이 배포된 워커가 **조용히 동시성 1로
돌지 않고 부팅을 거부**했다. 조용히 돌았다면 72h 제출 창에서 8배 느린 큐를 아무도
모르게 얻었을 것이다.

★**단, 그 둘은 `activeDeployments=1`이다** -- Railway가 배포를 여전히 "활성"으로 들고
있고 상태만 CRASHED다. 즉 **누가 그 프로젝트에 `WORKER_CONCURRENCY`를 세팅하면 그 순간
부팅해서 클레임 경쟁에 복귀한다.** 3중 경합은 제거된 게 아니라 **환경변수 하나 뒤에
있다.** 발사 전 확인 대상으로 올린다(배포·env는 대표님 소관).

## 8. 신고 -- 새 파일 2개

| 파일 | 성격 |
|---|---|
| `scripts/inspect-i2v-b-preflight.mjs` | **읽기전용.** 시즌 해석·카탈로그 단가·길이 경계·배우/참조·잔액·캡·워커 생존·과거 i2v 잡 전체의 fal 입력 덤프 |
| `scripts/i2v-b-realcall.mjs` | **기본 dry-run.** `--confirm`으로만 지출. `--watch <id>` / `--verify <id>`로 재감시·산출물 검증 단독 실행. 지출 전 가드 5종(dev-mode env / 큐 비었음 / 단가·크레딧이 승인 봉투와 일치 / 배우+참조 / 부모 이미지) |

★두 스크립트 모두 **로컬 워커를 띄우지 않는다.** `--confirm`은 job을 만들고 **읽기만**
하며 기다린다. 어제의 near-miss(로컬 워커가 프로덕션 job을 가로채고 모델·길이를 조용히
치환)를 구조적으로 못 하게 한 것이 아니라 **하니스가 그 짓을 안 하도록** 만든 것이다 --
사람이 따로 워커를 띄우면 여전히 가로챌 수 있다.
