# 채점 3사 잔액 선점검 + 조기감지 설계 (2026-09-07)

본부 지시: 9/6(OpenAI) · 9/7(Anthropic) 이틀 연속 벤더 잔액 소진 사고. 실전 500편
중간에 나면 조용히 멈춘다 — 설계만, 아직 미구현.

## 1. 조사 — 3사에 "잔액 조회 API"가 있는가

지금 코드가 들고 있는 자격증명(프로젝트/개인 API 키)을 기준으로 조사:

| 벤더 | 잔액 조회 API | 비고 |
|---|---|---|
| Anthropic | **없음** | 표준 Messages API 키로는 잔액/한도 엔드포인트가 없다. Console 웹 대시보드만 표시. Admin API(조직 관리용, 별도 admin 키)가 최근 생겼는데 그 안에 잔액 엔드포인트가 있는지는 확인 못 했다 — 내 지식 컷오프 이후 바뀌었을 수 있어 **재확인 필요**, 있으면 설계 A를 진짜 잔액조회로 업그레이드 가능. |
| OpenAI | **없음(지금 키로는)** | 프로젝트 API 키에는 잔액 엔드포인트가 없다. 조직 Admin API(`/v1/organization/costs`, `/v1/organization/usage/*`)가 있지만 이건 **사용량**이지 **잔액**이 아니고, 별도 Admin 키가 필요하다(지금 키와 다름, 발급하려면 본부 판단). |
| Google (Gemini API key / AI Studio) | **없음** | API 키 레벨에서는 잔액 개념 자체가 없다. Vertex AI로 전환해 GCP 프로젝트 청구에 묶으면 Cloud Billing Budget API + 예산 알림(Pub/Sub)으로 가능하지만, 지금 구조(API 키 직접 호출)와 아키텍처가 다르다 — 별건. |

**결론**: 지금 갖고 있는 자격증명으로는 3사 다 "잔액을 물어보는" 방법이 없다. 그래서
"선점검"은 잔액 조회가 아니라 **카나리아 호출**(최소 비용 실호출 1건으로 그 벤더가
지금 응답 가능한지 확인)로 구현해야 한다 — 진짜 잔액이 아니라 "지금 이 순간 거부되고
있는가"만 알 수 있다는 한계를 그대로 안고 간다.

## 2. 설계 A — 배치 시작 전 프리플라이트

시즌 채점 tick(batch.ts main() 시작 시점, 매번 또는 하루 1회)에:

1. 3사 각각에 **최소 비용 캐노니컬 호출**(프레임 1장, max_tokens 최소, 텍스트만이면
   더 저렴) 1건씩 시도.
2. 전부 성공 → 정상 진행.
3. 하나라도 빌링 시그니처 오류(아래 §3 패턴)로 실패 → **이번 tick 전체 스킵**
   (신규 후보 0건 pick) + 즉시 admin 메일(어떤 벤더, 몇 시, 원문 오류 메시지).
4. 메일 본문에 "이 시즌 남은 pickPending 대상 수 × 최근 실측 벤더별 평균단가"로
   추산한 예상 소요 비용을 같이 적는다 — ★이건 "얼마 필요한가"의 답이지 "잔액이
   얼마 남았는가"의 답이 아니다(§1의 한계). 진짜 잔액 대조가 아니라 관리자가 크레딧을
   얼마나 채워야 할지 가늠할 참고치로만 쓴다.

카나리아 호출 비용은 무시 가능(호출당 1센트 미만) — 매 tick(시간당)마다 태우는 것과
하루 1회만 태우는 것 중 어느 쪽으로 할지는 정책 결정(§5).

## 3. 설계 B — 도는 중 조기감지

`classifyError`(scorer.ts)에 **세 번째 분류 `'billing'`**을 신설한다(현재는
transient/permanent 둘뿐):

```
billingPatterns = /credit balance|insufficient_quota|exceeded your current quota|billing|please (go to|visit) (plans|billing)/i
```

동작:
- 슬롯 호출이 `billing`으로 분류되면 **그 벤더에 대해 이번 tick 나머지 후보 호출을
  즉시 중단**한다(다음 candidate로 넘어가되 그 벤더는 더 안 부름, 또는 tick 자체를
  끝냄) — 어차피 확정적으로 또 거부당할 gpt/gemini 호출까지 낭비하며 여러 편을
  헛되이 태우지 않는다. ★현재 코드는 이 구분이 없어서, 한 벤더가 죽으면 후보마다
  나머지 두 벤더 비용만 계속 나가며 조용히 실패가 쌓인다(오늘 실측 재현).
- **즉시 admin 메일**(기존 `sendAdminAlertOnceDaily` 재사용, 키를
  `vendor_billing_${vendor}_${date}`로 벤더별/일별 스로틀 — 하루 한 번은 반드시
  가되 같은 벤더로 계속 실패해도 메일 폭탄은 안 남).
- **reserve로 넘기지 않는다** — 정규 심사관이 계정 문제로 막힌 건데 예비 심사관에
  넘겨봐야 근본 원인 해결이 아니고(예비도 같은 방식으로 막힐 수 있음) 돈만 더
  나간다. 대신 슬롯을 `error_transient`처럼 취급해 크레딧이 채워지면 다음 tick에
  같은 벤더로 자동 재개되게 한다. 무한 대기 방지용 상한은 필요(§5, 값 미정).

## 4. 오늘 실측이 이 설계를 뒷받침하는 근거

- 9/7 Anthropic 크레딧 소진 재현: `V1-0907-cf_aquelle`에서 claude가 400으로
  거부됐는데, 코드가 이걸 그냥 `error_permanent`로 취급 — 다음 후보들도 계속
  claude를 불렀고(무해했던 이유는 400 자체가 무료 거부라서였을 뿐, gpt/gemini는
  그때마다 정상 과금됨), 아무도 알림을 못 받았다. 내가 로그를 직접 읽어서 발견했다 —
  자동 감지가 없으면 실전에서는 admin이 뒤늦게 RECHECK/PENDING 무더기를 보고서야
  알아챈다는 뜻.

## 5. 확인·판단 필요(임의로 안 정함)

1. **벤더 하나가 죽으면 배치 전체를 멈출지, 2/3 유효로 계속 갈지** — 실전 500편
   중간 사고 시 어느 쪽이 사업적으로 나은지는 본부 판단. (이 설계는 "즉시 알림"까지만
   자동화하고, 계속/중단 정책 자체는 아직 안 정했다.)
2. **Anthropic Admin API에 잔액 엔드포인트가 실제 있는지** — 최신 문서 재확인 필요
   (있으면 §1 표를 갱신하고 설계 A를 진짜 잔액조회로 승격).
3. **카나리아 호출 빈도** — 매 tick(현재 프로덕션 cron `0 * * * *`, 시간당)마다 할지
   하루 1회로 줄일지.
4. **billing 슬롯의 재시도 상한** — 무한 대기 방지용 상한값 미정, 크레딧이 언제
   채워질지는 사람 일이라 코드로 예측 불가.

## 6. 다음 단계

호출 + `sendAdminAlertOnceDaily` 벤더별 키 배선을 구현한다. 아직 코드 변경 없음 —
지시대로 설계만 먼저 올린다.
