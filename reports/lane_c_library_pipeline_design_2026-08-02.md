## 0. 지금 있는 것 / 없는 것 (실측)

**그대로 쓰인다 — 다시 만들지 마라**

| 부품 | 위치 | B안에서의 역할 |
|---|---|---|
| 게이트 master | `lib/music-gate.ts` `isMusicEnabled` | **이게 곧 라이브러리 스위치**다. SQL 한 줄 |
| 테이블 | `studio_music_assets` (27컬럼) | `source='library'` 절반 |
| v1m 서명 | `buildMusicAssetBind` / `verifyMusicAssetBind` | 필수 (findings ③) |

| 렌더 해석 | `studio.ts:1338 resolveMusicSignature` | source 무관하게 검증 |
| 믹싱 | 워커 렌더 경로 | 완성 |

**없는 것 — 이번 파이프라인의 실제 범위**

1. **대량 적재 수단이 없다.** `seed-music.ts`는 `MUSIC_FILE`/`MUSIC_ID`/`MUSIC_TITLE`/
   `MUSIC_MOOD` 환경변수 4개를 받는 **1회 1곡** 도구다. 300곡이면 손으로 300번이다.
2. **300곡을 고를 수 있는 UI가 없다.** 현재 피커는 `<select>` 하나이고 옵션 라벨이
   `{mood} — {title}`이다(`ProComposeEditor.tsx:1762~1765`). 미리듣기 없음, 필터 없음,
   페이지네이션 없음. 게다가 `listMusicAssets`가 **전량을 페이지 페이로드에 실어 보낸다**.
3. **분류할 컬럼이 없다.** 라이브 27컬럼 중 분류용은 `title`과 `mood` **자유문자열 2개**.
   `genre`/`bpm`/`tags`/`sort_order` **전부 부재**(실측).
4. **라이선스 기록의 라이브러리판이 없다.** 프로버넌스 4컬럼
   (`provider`/`provider_model`/`provider_generated_at`/`license_type`)은 **워커 AI 경로만**
   쓴다. `seed-music.ts`는 하나도 안 쓴다 → 300곡 전부 NULL이 된다.
   **컬럼을 만든 이유가 정확히 이 경우**인데 지금 구조로는 안 채워진다.
5. **큐레이션 운영 수단이 없다.** `active` 컬럼은 있는데 그걸 끄고 켜는 화면이 없다.
   곡 하나 내리려면 SQL이다.
6. **라이브러리 행은 현재 0행**이다. 이전할 자산이 없다 = 마이그레이션 부담도 없다.

## 1. 설계 원칙 4개

**P1. 곡의 정체성은 파일명이 아니라 `id`다.**
`id`는 TEXT PK이고 v1m 서명 안에 들어간다(`v1m|assetId|source|contentHash`).
파일명에서 유도하면 파일 하나 이름 바꾸는 순간 중복 300곡이 된다.
→ **매니페스트가 id의 원본**이고, 재적재는 매니페스트 기준 upsert다.

**P2. 라이선스 값은 엔지니어가 채우지 않는다.**
③a에서 이미 정한 규율 그대로다 — 불리언은 계약 원문에서 오고 라벨은 우리 분류기가
붙인다. 라이브러리도 동일하게 간다. **곡마다가 아니라 배치(=계약)마다** 선언한다.

**P3. 미분류 곡은 적재되지 않는다(fail-closed).**
라이선스를 말할 수 없는 곡이 `active=true`로 들어가는 경로를 만들지 않는다.
"나중에 채우자"가 300개 NULL로 남는 게 이 프로젝트의 실제 실패 패턴이었다.

**P4. 테마 종속 결정은 데이터로 미룬다.**
장르·무드 목록을 코드에 쓰지 않는다. 어떤 축으로 나눌지 본부가 정하기 전에는
**축의 개수조차 확정하지 않는다** — 2절에서 두 안을 병렬로 남겨 둔 이유다.

## 2. ★분류 그릇 — 두 안, 결정은 vocabulary가 온 뒤

300곡을 `mood` 자유문자열 하나로 고르게 할 수는 없다. 다만 **몇 축이 필요한지는
vocabulary가 정한다**. 그래서 여기서 하나로 못 좁히고, 두 안의 **비용 차이**만 확정해 둔다.

### 안 A — 컬럼 추가 (마이그레이션 1건)

`genre` / `bpm` / `sort_order` 같은 실제 컬럼을 붙인다.

- 장점: 인덱스·필터·정렬이 정직하다. 어드민 화면이 단순해진다.
- 비용: **마이그레이션 → TK Run → 그 다음 코드 push** 순서 강제
  ([[feedback-migration-before-code-push]]). 축이 바뀌면 또 마이그다.

### 안 B — `mood`를 구조화 토큰으로 (마이그레이션 0건)

`mood`에 `genre=ambient;energy=low` 같은 규약 문자열을 넣고 앱이 파싱한다.

- 장점: 마이그 없음. 축을 바꿔도 데이터만 바뀐다.
- 비용: DB가 검증해 주지 않는다. 오타가 조용히 새 카테고리가 된다.
  **`mood`는 지금 피커 라벨로 그대로 노출**되므로(`{mood} — {title}`) 표시 문자열과
  분류 키를 겸하게 된다 — 이건 나중에 반드시 갈라야 한다.

★**내 권고: 안 A.** 300곡은 임시 규모가 아니라 시즌0 내내 쓰는 카탈로그이고,
`mood` 하나에 두 역할(표시·분류)을 겹치는 건 이미 한 번 데인 패턴이다.
**단, 마이그레이션 SQL은 vocabulary를 받은 뒤에 쓴다** — 축을 모르고 컬럼을 만들면
그게 바로 "설명할 수 없는 상수"다.

## 3. 파이프라인 5단계 (테마 무관분만)

```
[0] 매니페스트        곡 목록 + id + 라이선스 배치 참조   ← 사람이 만든다
[1] 배치 적재         업로드 → 해시 → v1m 서명 → upsert   ← seed-music.ts 확장
[2] 프로버넌스 기록   배치 단위 라이선스 4컬럼 주입        ← 신규
[3] 큐레이션          active on/off + 검수                ← 신규(최소)
[4] 피커              필터 + 미리듣기 + 페이로드 축소      ← 기존 UI 교체
```

### [0] 매니페스트

한 파일이 한 배치(=한 라이선스 근거)를 기술한다. 필드는 최소로:
`id`(안정 PK) / 파일 경로 / `title` / 분류 축(2절 결정에 따름) /
배치 공통 라이선스 참조. **곡별 라이선스 필드는 두지 않는다** — 곡마다 다르면
그건 배치가 아니라 다른 계약이고, 파일을 나눠야 한다.

★재실행 안전: 같은 `id` + 같은 바이트 = 아무 일도 안 일어남(해시 동일).
같은 `id` + 다른 바이트 = 서명 재계산 + upsert. **다른 `id` + 같은 바이트 = 중복** —
이걸 막으려면 적재 시 content hash 충돌 검사가 필요하다(현재 없음).

### [1] 배치 적재

`seed-music.ts`를 **버리지 말고 감싼다.** 지금 로직(ffprobe 길이 → R2 `music/` 업로드
→ `hashMusicAsset` → `buildMusicAssetBind` → upsert)은 정확하다. 필요한 건
**환경변수 인터페이스를 매니페스트 루프로 바꾸는 것**과, 실패한 곡에서 멈추지 않고
**끝까지 돌고 실패 목록을 내는 것**이다(300곡짜리 작업이 137번째에서 죽으면 안 된다).

★**병렬도는 낮게.** R2 업로드는 우리 계정 대역폭이고, 어차피 사람이 한 번 돌리는
배치다. 빠를 이유가 없다.

### [2] 프로버넌스 기록

`license_type`은 **분류기(`lib/music-license.ts`)가 붙인다.** 배치 매니페스트가
선언하는 건 계약 사실(불리언 + 인용)이고, 라벨은 우리가 매긴다 — AI 경로와 동일한 규율.
분류 불가 = **그 배치 전체 적재 거부**(P3).

★`provider`/`provider_model`이 라이브러리에서 뜻하는 바가 AI 경로와 다르다.
AI는 "우리가 호출한 벤더/모델"이고, 라이브러리는 "이 곡을 만든 출처"다. 값의 의미가
다르니 **컬럼 주석 또는 문서에 명시**하지 않으면 나중에 집계가 섞인다.

### [3] 큐레이션 (최소)

발사에 필요한 건 "곡 하나 내리기"뿐이다. `active` 토글 + 목록.
★**감상용 재생이 붙는 순간 어드민이 아니라 미디어 화면이 된다** — 범위를 지켜야 한다.
어드민 노출 자체가 발사 필수인지는 ⑦-1과 같은 종류의 질문이고, **대표님 결정**이다.

### [4] 피커

세 가지가 필요하고, 셋 다 지금 없다:
1. **필터** — 2절의 축으로. 300개 `<select>`는 못 쓴다.
2. **미리듣기** — 들어보지 않고 고르는 건 고르는 게 아니다. R2 URL은 이미 공개다.
3. **페이로드 축소** — 지금 `listMusicAssets`는 전량을 스튜디오 페이지 응답에 싣는다.
   음악을 안 쓰는 참가자도 300행을 받는다. **음악 패널 열 때 별도 조회**로 바꾼다.

★이 셋 중 **3번은 테마와 완전 무관**하므로 vocabulary를 기다릴 필요가 없다.
1·2번은 축이 정해져야 화면이 정해진다.

## 5. 이 설계가 건드리지 않는 것 (명시)

- **music 레인·provider 경계·rate limit·리스**: B안에서 안 쓰이지만 **시즌1 C안에서
  쓰인다. 삭제 금지.** 라이브러리 경로와 코드가 겹치지 않으므로 공존에 비용이 없다.
- **v1m canonical**: 손대지 않는다. KAT 골든 앱 83/83 · 워커 22/22 무변화가 조건이다.
- **`lib/studio.ts`의 A 소유 구역**(`submitRender`/`finalizeSubmission`/스위프):
  이 파이프라인은 `listMusicAssets` 한 곳만 만진다.
