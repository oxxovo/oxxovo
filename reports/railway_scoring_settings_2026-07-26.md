# 채점 워커 Railway 설정 변경 — TK 실행용 (2026-07-26)

근거 = `reports/scoring_500_throughput_2026-07-26.md`.
**이 변경을 안 하면 500편 채점에 약 250h가 걸려 72h 창을 178h 초과한다.**
엔진은 충분히 빠르다(500편 10.6h). 바꾸는 건 **처리량 설정 2개**뿐이다.

# TK님 단계별 안내 (화면 순서대로)

## STEP 0 — 들어가기

1. https://railway.app 로그인 → 대시보드에 프로젝트 카드들이 보입니다.
2. 채점 워커가 들어 있는 프로젝트를 엽니다(`oxxovo-scoring` 레포로 만든 서비스가 들어 있는 프로젝트).
3. 열면 **캔버스 화면**에 서비스 박스들이 떠 있습니다. `oxxovo-scoring` 이름이 붙은 박스가 **2개** 보일 겁니다
   (이름이 같거나 비슷하게 붙어 있을 수 있습니다).

## STEP 1 — ★둘 중 "예선" 잡 고르기 (제일 헷갈리는 부분)

박스 이름만으로는 구분이 안 될 수 있으니 **Variables로 판별**합니다. 두 박스를 각각 클릭해서:

1. 서비스 박스 클릭 → 상단 탭 중 **`Variables`** 클릭.
2. 변수 목록에서 **`ROUND`** 를 찾습니다.

| 보이는 것 | 이 서비스는 | 이번에 |
|---|---|---|
| `ROUND` 가 **목록에 없음** | **예선 잡** | ★이걸 바꿉니다 |
| `ROUND = main` 이 있음 | 본선 잡 | 손대지 않습니다 |

- 두 번째 판별법: **`Settings`** 탭 → **Start Command** 가
  `node dist/batch.js` = 예선 / `ROUND=main node dist/batch.js` = 본선.
- 만약 **두 박스 다 `ROUND` 가 없다면** 본선 잡이 아직 안 만들어진 것이고, 지금 보는 게 예선 잡입니다(그대로 진행).

> 확신이 안 서시면 그 화면 그대로 두시고 저(지수2)에게 두 서비스의 이름 + Variables 목록만 알려주십시오.
> 제가 어느 쪽인지 짚어 드립니다. **잘못된 쪽을 바꾸면 예선이 안 돌거나 본선이 두 번 돕니다.**

## STEP 2 — BATCH_SIZE 바꾸기 (예선 잡, Variables 탭)

1. 예선 잡 선택 → **`Variables`** 탭.
2. 목록에서 **`BATCH_SIZE`** 를 찾습니다.
   - **있으면**: 값 옆의 연필/점3개 아이콘 → 값을 **`30`** 으로 고치고 저장.
   - **없으면**: `+ New Variable` 버튼 → 이름 `BATCH_SIZE`, 값 `30` → 저장.
3. 저장하면 Railway가 "Apply / Deploy" 를 요청할 수 있습니다 → **적용(Deploy)** 눌러 반영합니다.

## STEP 3 — Cron 주기 바꾸기 (예선 잡, Settings 탭)

1. 같은 서비스에서 **`Settings`** 탭.
2. 아래로 내려가 **`Cron Schedule`** 항목을 찾습니다.
3. 지금 값이 `*/30 * * * *` 이면 지우고 아래를 넣습니다:

```
0 * * * *
```

4. 저장(Update/Save). 별표 순서를 헷갈리지 마십시오 — **맨 앞이 0, 뒤에 별표 4개**입니다.
   (`0 * * * *` = 매시 정각 1회. `* 0 * * *` 로 잘못 넣으면 자정에 1분마다 60번 돕니다.)

## STEP 4 — 같이 확인만 (예선 잡, Variables 탭)

바꾸는 게 아니라 **값이 맞는지 눈으로만** 확인하시면 됩니다.

| 변수 | 있어야 할 상태 |
|---|---|
| `SEASON_REQUIRED_STATUS` | 값이 **비어 있어야** 합니다. `scoring` 이라고 적혀 있으면 지워서 빈 값으로 저장 |
| `SEASON_ID` | `season_0` (없어도 코드 기본값이 같아서 동작은 합니다) |
| `ROUND` | 없어야 합니다 (있으면 STEP 1을 잘못 고른 것) |

## STEP 5 — 잘 됐는지 확인

- 다음 **정각**이 지난 뒤 그 서비스의 **`Deployments`** 탭 → 최근 실행 로그를 엽니다.
- 로그에 영상 여러 편을 연속으로 처리하는 줄이 보이면 성공입니다(전에는 1편만 처리하고 끝났습니다).
- 처리할 영상이 없으면 "0건"으로 즉시 끝납니다 — **정상**이고 비용도 들지 않습니다. 지금은 신청이 없어서
  이 상태가 맞습니다. 설정만 미리 걸어두는 것입니다.

## 하면 안 되는 것

- 본선 잡(`ROUND=main`)의 값은 **건드리지 마십시오**. 본선은 50편이라 지금 설정으로 충분합니다.
- 예선 잡을 **복제해서 2개로 늘리지 마십시오**. 두 잡이 같은 영상을 붙잡고 충돌합니다(아래 "하지 말 것" 참조).

## 어디를 바꾸나 — 서비스 특정

Railway 프로젝트 안에 `oxxovo-scoring` 레포로 만든 서비스가 **2개** 있다
(둘 다 `railway.json`: Dockerfile 빌드 + `restartPolicyType: NEVER` = 1회 실행 후 종료하는 scheduled job).

| 구분 | 어떻게 알아보나 | 이번에 바꿀 대상 |
|---|---|---|
| **예선 잡** | Variables에 `ROUND` 가 **없음**(기본값 = `application`). Start Command = `node dist/batch.js` | **★이것** |
| 본선 잡 | Variables에 `ROUND=main` 있음, 또는 Start Command = `ROUND=main node dist/batch.js` | 지금은 그대로 |

예선 잡이 9/3~9/5 예선심사 창에서 500편을 도는 잡이다. 본선은 50편이라 현재 설정으로도 충분하다.

## 바꿀 값 2개 (예선 잡)

### 1. Variables 탭 → `BATCH_SIZE`

```
BATCH_SIZE = 30
```

현재 값은 `1`(코드 기본값도 `1`). 이 값 = **cron 1회 실행당 처리할 영상 편수**.
`batch.ts`는 한 번 깨어나 BATCH_SIZE개를 **직렬로** 채점하고 종료한다.

### 2. Settings 탭 → Deploy → **Cron Schedule**

```
0 * * * *
```

현재(문서 권장치) `*/30 * * * *`. 매시 정각 1회로 바꾼다.

### 왜 이 조합인가

| cron | BATCH_SIZE | 1회 소요 | 500편 총 | 판정 |
|---|---|---|---|---|
| `*/30` | 1 | 1분 | **250h** | 72h를 178h 초과 |
| `*/5` | 1 | 1분 | 42h | OK |
| **`0 * * * *`** | **30** | **38분** | **17h** | **OK (여유 4.2배) ← 권장** |
| `0 * * * *` | 40 | 51분 | 13h | OK |

1회 38분 < 주기 60분이라 실행이 겹치지 않는다(전 편이 p90 100s/편인 최악에도 50분).
1,000편으로 늘려도 34h로 72h 안에 들어간다.

## 같이 확인할 것 (예선 잡 Variables)

| 변수 | 있어야 할 값 | 안 맞으면 |
|---|---|---|
| `SEASON_REQUIRED_STATUS` | **빈 문자열** (`SEASON_REQUIRED_STATUS=`) | 기본값이 `'scoring'`인데 season-tick에 그런 상태가 없어 **0건으로 조용히 종료**. 채점이 아예 안 돈다 |
| `SEASON_ID` | `season_0` | 미설정이어도 코드 기본값이 `season_0`이라 동작은 함. 명시 권장 |
| `ROUND` | (없음 = application) | `main`이 들어가 있으면 예선을 안 돈다 |
| `MAX_RETRIES` | 3 (기본) | 그대로 |

## 하지 말 것

- **예선 잡을 2개로 늘려 병렬 처리하지 말 것.** `pickPending`이 항상 50행 윈도의 첫 행을 집어
  두 잡이 같은 행에서 충돌하고, 진 쪽이 배치 전체를 조기 종료한다(데이터 손상은 없고 처리량만 손실).
  여유가 6.8배라 병렬화 자체가 불필요하다.
- 채점이 다 끝난 뒤 cron을 굳이 끌 필요는 없다 — 대상이 없으면 0건으로 종료한다(무비용).

## 변경 후 확인

1. Railway 예선 잡 → Deployments 로그에서 다음 정각 실행이 `BATCH_SIZE=30`으로 돌았는지.
2. `scoring_results`에서 해당 시각 `started_at` 행 수가 늘어나는지.
3. 리허설로 미리 검증하려면 `SEASON_ID=season_test`로 동일 조합을 한 번 돌려본다.
