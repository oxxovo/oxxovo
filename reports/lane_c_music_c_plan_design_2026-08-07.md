## 0. 전환으로 뒤집히는 것 (08-02 문서 §5 정정)

08-02 문서는 §5에서 **"music 레인·provider 경계·rate limit·리스는 B안에서 안 쓰이지만
시즌1 C안에서 쓰인다"**고 적었다. **시즌0에서 쓰인다.** 그 목록 전체가 발사 경로로
들어온다: 워커 music 레인 · provider 경계 · rate limit · 리스 · claim_token ·
환불 멱등 · 과금 · 프로버넌스 · 지출 집계 · 가격 fail-closed.

★**캡 15가 되살아난다.** 08-02 findings ④는 `studio_music_max_generations_per_round`를
**사문화**로 판정했다 — 캡을 읽는 두 곳이 `aiEnabled` 뒤에 있었기 때문이다. C안은
`aiEnabled`를 켜므로 **그 판정이 무효가 되고 캡이 다시 유효 규칙이 된다.**
라이브 실측: `season_0.studio_music_max_generations_per_round = **15**`.

## 1. ★이미 되어 있는 것 — C안에서 다시 만들 필요 없는 것

| 부품 | 실측 | C안에서 |
|---|---|---|
| 두 출처 합집합 피커 | `listMusicAssets:1344` = `(source='library' AND active) OR (source='ai' AND user_id=본인)` | **이미 정확하다.** 남의 AI 곡은 안 보인다 |
| 렌더측 소유 검증 | `resolveMusicSignature` + 워커 `getRenderMusicPath`: `source==='ai' && user_id!==render.user_id` → 거부 | 그대로 성립 |
| 선택은 과금 경로가 아니다 | `pickMusic`은 EDL 상태만 바꾼다. 렌더·제출 어디에도 곡 선택 과금이 없다 | **무상이 이미 구조다** |
| 가격 fail-closed | `validateMusicPricing` → `music_not_priced` | 아래 3절 |

★**"고르기=무상"은 새로 만들 게 없다.** 선택 경로에 과금 코드가 애초에 없다.

## 2. ★무상/유상 경계 — 실제 위험은 "가격 오표시"가 아니다

제니2 지시: *"같은 화면에서 두 경로가 다른 과금 규칙을 갖는다. 그 경계가 UI와 서버
양쪽에 서야 한다 — 한쪽만 알면 '무료인 줄 알고 눌렀는데 과금'이 된다."*

경계를 다시 그으면 **항목이 아니라 동작** 사이에 있다:

```
[고르기]  라이브러리 곡  ─┐
[고르기]  내가 전에 생성한 AI 곡 ─┤→ 무상 (읽기. 실패 모드 없음)
[생성]    새 AI 곡 ────────────┘→ 유상 (원가×1.25, 캡 15, 잔액·가격 검사)
```

★**내가 전에 생성한 AI 곡을 다시 고르는 것도 무상이다** — 과금은 생성 시점에 이미
끝났다. 즉 피커 안의 모든 항목은 무상이고, **유상인 것은 패널 안의 "생성" 버튼 하나뿐**이다.

### 그래서 서버 쪽은 이미 서 있다 (실측)

두 진입점이 이미 갈라져 있다: `listMusicAssetsAction`(읽기, 과금 코드 없음) /
`createMusicGenerationAction`(과금, 캡, 잔액, 가격 fail-closed).
**설계의 일이 "만들기"가 아니라 "고정하기"다** — 아래 4절 테스트.

### ★UI 쪽의 실제 갭 = 무상 경로가 자기가 무상임을 말하지 않는다

유상 쪽은 이미 말한다: `music_ai_cost(n)` 크레딧 · `music_ai_remaining(left, cap)` ·
`music_ai_refund_note`. **무상 쪽은 아무 말도 안 한다.** 곡 `<select>` 옆에는 가격도,
"무료"도 없다.

★그래서 오해의 방향은 제니2가 경계한 것의 **반대**다: 값이 틀리게 붙어 있는 게 아니라,
**값이 없는 동작이 값이 있는 동작 바로 옆에 있다.** 참가자는 "여기 어딘가 크레딧이
든다"를 보고 **선택도 유상일까 봐 안 누른다** — 무상 라이브러리를 안 쓰는 쪽으로 틀린다.

**설계 결론(3줄 규모, UI만)**
1. 피커 라벨에 **"무료"/"Free"** 명시. 300곡을 준 이유가 여기서 사라지지 않게.
2. 생성 버튼은 **누르기 전에** 가격·잔액·남은 횟수를 한 줄로. (가격·횟수는 이미 있음 →
   잔액을 같은 줄로 옮기는 것뿐)
3. 두 블록을 **시각적으로 분리**(구분선/제목). 지금은 한 카드 안에 이어져 있다.

★문구 자체는 확정 아님 — 위 3건은 **자리**의 설계다. 문구는 제니2 승인 뒤.

## 3. ★스위치 순서 — 지금 켜면 생성이 전부 실패한다

라이브 실측 2026-08-07:

| 키 | 값 |
|---|---|
| `seasons.studio_music_enabled` (season_0) | **false** |
| `seasons.studio_music_ai_enabled` (season_0) | **false** |
| `platform_config` 음악 가격 키 | **0개** (`studio_music_gen_cost_usd` 없음) |
| `studio_credit_usd_value` / `studio_margin_rate` | 0.10 / **0.25** |
| `studio_music_assets` 행 수 | **0** |

→ `studio_music_ai_enabled`만 먼저 켜면 `validateMusicPricing`이
**`music_not_priced`로 전량 거부**한다. **이건 결함이 아니라 fail-closed가 작동하는
모습**이고, 순서를 지키면 안 보인다:

```
1. 300곡 적재 (source='library', active=true)      ← 코드는 준비됨(seed:music:batch)
2. platform_config 음악 가격 키 설정               ← 없으면 생성 전량 거부
3. seasons.studio_music_enabled = true             ← 라이브러리 노출
4. seasons.studio_music_ai_enabled = true          ← 생성 노출
```

★1·2·3·4 전부 **DB 쓰기라 지수 본체/대표님**이다. 내가 SQL을 만들지 않는다(⑥).
★2를 3보다 **먼저** 하는 이유: 3만 켜도 참가자에게 음악 패널이 보이고, 그 시점에 4가
꺼져 있으면 생성 블록은 안 보이므로 안전하다. 반대로 4를 2보다 먼저 켜면 참가자가
"생성 실패"를 본다.

## 4. ★고정할 것 — 경계는 테스트로 서야 한다

경계가 코드에 이미 있으므로 위험은 "없다"가 아니라 **"조용히 사라진다"**다.
제안(코드 0줄, 승인 후 구현):

1. **선택은 어떤 경우에도 원장을 건드리지 않는다.** `listMusicAssetsAction` 호출 전후
   `credit_transactions` 카운트 동일. 라이브러리 곡·본인 AI 곡 양쪽으로.
2. **가격 미설정 = 생성 거부, 그러나 선택은 정상.** 가격 키 부재 상태에서
   `createMusicGeneration` → `music_not_priced` **이면서** 목록은 정상 반환.
   ★이 조합이 지금 라이브 상태이므로 오늘 그대로 검증 가능하다.
3. **캡 15가 실제로 막는다.** 15회 후 16번째가 `music_cap_reached`, 그리고 **그 시점에도
   라이브러리 선택은 무상으로 된다**(캡이 무상 경로를 오염시키지 않는다).
4. **남의 AI 곡은 목록에 없고 렌더에서도 거부된다.** 두 참가자 데이터로 양방향.

★3·4는 행을 만들어야 하므로 `e2e/i2v-reference-guard.mjs`와 같은 규율을 따른다 —
전용 e2e 유저, 끝에 삭제, 삭제 자체를 단정.

## 5. ★300곡 격자 — 범용, 중립어, 착수 가능

본부 확정: 시즌명·테마와 **무관하게** 착수 가능. 금지: **화장품·코스메틱·CF용** 등
제품군·업종·광고형식 어휘. → 무드·장르 중립어만.
(같은 규칙을 코드에 대해 강제하는 체크가 이미 있다: `npm run test:theme-leak`.)

**제안 격자 (승인 대상)**

| 축 | 값 | 개수 |
|---|---|---|
| `genre` | ambient / cinematic / orchestral / electronic / acoustic / pop / hip-hop / rock | 8 |
| `mood` | calm / warm / bright / tense / melancholy / triumphant | 6 |
| `tempo` | slow(<90) / mid(90–120) / fast(>120) | 3 |

8 × 6 = **48 셀 × 6곡 ≈ 288곡** (300에 맞음). `tempo`는 격자 축이 아니라 **필터**다 --
축으로 올리면 144셀이 되고 셀당 2곡은 "고를 수 있다"가 아니다.
★중립성 자체 점검: 위 17개 값 중 제품군·업종·광고형식 어휘 **0개**.

**08-02 §2의 A/B 결정 — 이제 A로 확정 가능하다.** 그 문서가 A를 못 고른 이유는
"축을 모르고 컬럼을 만들면 설명할 수 없는 상수"였고, **축이 정해졌으므로 그 반대
사유가 사라졌다.** 필요한 컬럼: `genre` TEXT · `bpm` INT · `sort_order` INT
(`mood`는 이미 있다).
★**마이그레이션 SQL은 내가 만들지 않는다(⑥)** — 컬럼 목록만 여기 남기고 본체가 쓴다.
그리고 [[feedback-migration-before-code-push]] 순서: **마이그 Run → 코드 push.**

★`mood`가 지금 **표시 문자열과 분류 키를 겸한다**(`{mood} — {title}`). 격자가 들어오면
그 겹침을 끊어야 한다 — 표시는 `title`, 분류는 축 컬럼.

## 6. 파이프라인 — 생성 경로의 자리

```
[0] 매니페스트         곡 목록 + id + 배치 라이선스        ← 5절 격자 확정 후 착수 가능
[1] 배치 적재          업로드→해시→v1m→upsert            ← ✅ 완료 (seed:music:batch)
[2] 프로버넌스         배치 단위 4컬럼                     ← ✅ 골격, 값은 계약 대기
[3] 큐레이션           active on/off                       ← ❌ 범위 미정(대표님)
[4] 피커               필터·미리듣기·페이로드              ← 4-3 ✅ / 4-1,2 착수 가능(5절)
──────────────────────────────────────────────────────────
[1'] ★생성 경로 (신설, C안)   프롬프트→가격·캡·잔액→워커 music 레인→R2→v1m→같은 테이블
```

★`[1']`는 `[1]`의 형제다 — **같은 테이블, 같은 v1m, 같은 피커**로 합류하고 다른 것은
`source`와 **누가 소유하는가**뿐이다. 그래서 4절 테스트가 두 경로 공통 계약이 된다.
★워커 music 레인은 이미 있다(③a). C안은 그것을 **켜는** 것이지 만드는 것이 아니다.

## 7. ★C안 전환이 만드는 조용한 오작동 1건 (실측)

`listMusicAssets`(`lib/studio.ts:1332~1339`)는 이렇게 조회한다:

```
.eq('status','ready').not('url','is',null)
.order('source', { ascending: true })      ← 'ai' < 'library'
...그리고 source/user 필터는 SQL이 아니라 JS에서 적용된다(:1341)
```

**B안에서는 무해했다** — AI 행이 0이었다. **C안에서는 아니다.**

1. **`.limit()`이 없다.** PostgREST 기본 상한(Supabase `db-max-rows`, 통상 **1000**)이
   걸린다.
2. **정렬이 `source` 오름차순**이라 `'ai'`가 먼저 온다.
3. → 총 ready 행이 상한을 넘는 순간 **잘려 나가는 쪽이 `library`다.**

즉 시즌이 채워질수록 **참가자 피커에서 라이브러리 300곡이 조용히 줄어든다.** 캡 15 ×
참가자 수로, **AI 행 ~1000개**(≈67명 만사용)부터 시작된다. 에러도 경고도 없다.
부수적으로, 참가자 한 명의 피커 조회가 **다른 참가자들의 AI 행 전부를 읽어 온다**
(반환 전에 걸러지므로 유출은 아니지만, 500명×15 = 7,500행 + 300).

**고칠 방향**(4-1과 같은 작업에 흡수):
- 필터를 **SQL로**: `.or('source.eq.library,user_id.eq.<uid>')`
- **명시적 `.limit()`** + 격자 필터로 페이지 좁히기
- `active`도 SQL 조건으로

★**단정하지 않는 것**: Supabase 프로젝트의 실제 `db-max-rows`를 나는 못 읽었다(대시보드
설정). 1000은 기본값이다. **상한이 무엇이든 "AI가 먼저 정렬되고 라이브러리가 잘린다"는
순서는 값과 무관하게 성립한다** — 그게 이 항목의 요지다.

## 8. 착수 가능 / 대기

| 항목 | 상태 |
|---|---|
| 5절 격자 **승인** | ★제니2·본부 |

| 스위치 4단(3절) | ★본체·대표님 |

★공수 없음([[feedback-no-schedule-estimates]]). 진척은 위 표로 본다.
