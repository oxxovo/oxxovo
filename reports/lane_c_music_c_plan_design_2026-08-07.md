## 0. ★정책이 두 번 뒤집힌 뒤에 남는 규칙

> **정책 변경으로 무의미해진 코드는 지우지 말고 비활성으로 둔다.** (제니2, 2026-08-08)

물증이 이 문서 자신이다. `studio_music_max_generations_per_round`(=캡 15)를 08-02에
**"사문화"**로 판정했다 — 캡을 읽는 두 곳이 `aiEnabled` 뒤에 있었기 때문이다. 그
판정대로 지웠다면 **8/8 C안에서 다시 만들고, 8/8 B안에서 다시 지웠을 것**이다.
라이브 실측: `season_0.studio_music_max_generations_per_round = **15**`, 그리고 지금은
다시 **비활성**(`studio_music_ai_enabled=false`)이다. 값은 그대로 두고 켜지 않는다.

★**그리고 오늘 코드가 이 규칙을 이미 따랐다 — 되돌릴 코드가 0줄이다.**
`6f53715`의 수정을 **C안 전제로 쓰지 않고 경로 중립으로** 썼기 때문이다:

| 오늘 넣은 것 | B안 전용에서 |
|---|---|
| `listMusicAssets` SQL 필터·limit·정렬 | ★**그대로 필요**(아래 1절) |
| `musicPickerPathOk`의 `source==='ai'` 분기 | **비활성** — 그런 행이 생기지 않는다. 삭제 X |
| `resolveMusicSignature`의 제3 source 거부 | **경로 무관**. 그대로 유효 |
| `active` NULL = withheld | **경로 무관**. 라이브러리 전용에서 오히려 더 중요 |

★이게 "C안용 작업이 헛되지 않았다"는 뜻은 아니다. **경로별 분기를 쓰지 않고 규칙으로
썼기 때문에 전환 비용이 0이 된 것**이고, 다음에도 그렇게 쓰라는 것이 이 절의 요지다.

## 0b. [시즌1] C안 전제로 적었던 것 — 자리만 남긴다

08-02 문서 §5의 **"music 레인·provider 경계·rate limit·리스는 B안에서 안 쓰이지만
시즌1 C안에서 쓰인다"**는 판단이 **다시 유효하다.** 8/8 낮에 이 문서가 "시즌0에서
쓰인다"로 뒤집었던 것을 **되돌린다.** 해당 목록(워커 music 레인 · provider 경계 ·
rate limit · 리스 · claim_token · 환불 멱등 · 과금 · 프로버넌스 · 지출 집계 ·
가격 fail-closed)은 **시즌1 항목이고 삭제 대상이 아니다.**

## 1. ★이미 되어 있는 것 — 다시 만들 필요 없는 것

| 부품 | 실측 | 판정 |
|---|---|---|
| 두 출처 합집합 피커 | `listMusicAssets` = `(library AND active) OR (ai AND 본인)`, 이제 SQL 쪽 | **정확하다.** 시즌0에선 ai 절이 **비활성** |
| 렌더측 소유 검증 | `resolveMusicSignature` + 워커 `getRenderMusicPath`: `source==='ai' && user_id!==render.user_id` → 거부 | 그대로 성립 |
| 선택은 과금 경로가 아니다 | `pickMusic`은 EDL 상태만 바꾼다. 렌더·제출 어디에도 곡 선택 과금이 없다 | **무상이 이미 구조다** |
| 가격 fail-closed | `validateMusicPricing` → `music_not_priced` | 아래 3절 |

★**"고르기=무상"은 새로 만들 게 없다.** 선택 경로에 과금 코드가 애초에 없다.

## 2. [시즌1] 무상/유상 경계 — ★시즌0에서는 **잠복**한다

★**B안 확정으로 이 절 전체가 시즌0에서 발동하지 않는다.** 유상 동작이 화면에 하나도
없다 — 생성 패널은 `props.musicAiEnabled` 뒤에 있고 그 값이 false다. 그래서:

★**아래 (1)번 권고("피커에 무료 명시")를 철회한다.** 그 권고의 근거는 *"유상 동작이
바로 옆에 있어서 참가자가 선택도 유상일까 봐 안 누른다"*였다. **옆에 유상 동작이 없으면
그 근거가 사라진다.** 값이 하나도 안 붙은 화면에서 "무료"라고 말하는 것은 없던 의심을
만드는 쪽이다. 시즌1에 생성이 붙는 날 다시 유효해진다.
(2)·(3)도 같은 이유로 시즌1 항목이다.

★**그러나 서버 쪽 판정은 지금도 유효하다** — 선택 경로에 과금 코드가 없다는 사실과,
경로를 판정 못 하면 막는다는 규칙은 라이브러리 전용에서도 그대로 성립한다. 4절 테스트
1·2는 유지, 3·4는 시즌1.

아래는 원문 보존(시즌1 착수 시 그대로 쓴다).

### [원문] 무상/유상 경계 — 실제 위험은 "가격 오표시"가 아니다

제니2 지시: *"같은 화면에서 두 경로가 다른 과금 규칙을 갖는다. 그 경계가 UI와 서버
양쪽에 서야 한다 — 한쪽만 알면 '무료인 줄 알고 눌렀는데 과금'이 된다."*

경계를 다시 그으면 **항목이 아니라 동작** 사이에 있다:

```
[고르기]  라이브러리 곡  ─┐
[고르기]  내가 전에 생성한 AI 곡 ─┤→ 무상 (읽기. 실패 모드 없음)
[생성]    새 AI 곡 ────────────┘→ 유상 (원가×1.25, 캡 15, 잔액·가격 검사)
```

★**내가 전에 생성한 AI 곡을 다시 고르는 것도 무상이다** — 과금은 생성 시점에 이미
끝났다. 즉 피커 안의 모든 항목은 무상이고, **유상인 것은 패널 안의 "생성" 버튼 하나뿐**이다.

### 그래서 서버 쪽은 이미 서 있다 (실측)

두 진입점이 이미 갈라져 있다: `listMusicAssetsAction`(읽기, 과금 코드 없음) /
`createMusicGenerationAction`(과금, 캡, 잔액, 가격 fail-closed).
**설계의 일이 "만들기"가 아니라 "고정하기"다** — 아래 4절 테스트.

### ★UI 쪽의 실제 갭 = 무상 경로가 자기가 무상임을 말하지 않는다

유상 쪽은 이미 말한다: `music_ai_cost(n)` 크레딧 · `music_ai_remaining(left, cap)` ·
`music_ai_refund_note`. **무상 쪽은 아무 말도 안 한다.** 곡 `<select>` 옆에는 가격도,
"무료"도 없다.

★그래서 오해의 방향은 제니2가 경계한 것의 **반대**다: 값이 틀리게 붙어 있는 게 아니라,
**값이 없는 동작이 값이 있는 동작 바로 옆에 있다.** 참가자는 "여기 어딘가 크레딧이
든다"를 보고 **선택도 유상일까 봐 안 누른다** — 무상 라이브러리를 안 쓰는 쪽으로 틀린다.

**설계 결론(3줄 규모, UI만)**
1. 피커 라벨에 **"무료"/"Free"** 명시. 1,000곡을 준 이유가 여기서 사라지지 않게.
2. 생성 버튼은 **누르기 전에** 가격·잔액·남은 횟수를 한 줄로. (가격·횟수는 이미 있음 →
   잔액을 같은 줄로 옮기는 것뿐)
3. 두 블록을 **시각적으로 분리**(구분선/제목). 지금은 한 카드 안에 이어져 있다.

★문구 자체는 확정 아님 — 위 3건은 **자리**의 설계다. 문구는 제니2 승인 뒤.

## 3. ★스위치 순서 — 시즌0은 2단에서 끝난다

라이브 실측 2026-08-07:

| 키 | 값 |
|---|---|
| `seasons.studio_music_enabled` (season_0) | **false** |
| `seasons.studio_music_ai_enabled` (season_0) | **false** |
| `platform_config` 음악 가격 키 | **0개** (`studio_music_gen_cost_usd` 없음) |
| `studio_credit_usd_value` / `studio_margin_rate` | 0.10 / **0.25** |

★**B안 확정으로 스위치는 3단이고, 4단째를 "안 하는 것"이 곧 정책이다.**

```
1. 1,000곡 적재 (source='library', active=true)   ← 코드 준비됨(seed:music:batch)
2. seasons.studio_music_enabled = true            ← 라이브러리 노출

3. [시즌1] platform_config 음악 가격 키 설정        ← 없으면 생성 전량 거부
4. [시즌1] seasons.studio_music_ai_enabled = true  ← 생성 노출
```

★**가격 키 미설정이 지금은 "미완"이 아니라 "그래야 하는 상태"다.** 시즌0에 켤 생성이
없으므로 가격 키가 없어야 맞고, 만약 누군가 4를 먼저 켠다면 `validateMusicPricing`이
`music_not_priced`로 **전량 거부**한다 — 즉 **잘못된 순서가 사고가 아니라 거부로
끝난다.** 이건 결함이 아니라 fail-closed가 작동하는 모습이다.

★1·2 둘 다 **DB 쓰기라 지수 본체/대표님**이다. 내가 SQL을 만들지 않는다(⑥).
★시즌1에 3을 4보다 **먼저** 해야 하는 이유는 원래대로다: 4를 2보다 먼저 켜면 참가자가
"생성 실패"를 본다.

★용어 정리: 제니2 대기 목록의 "스위치 4단"은 이 문서의 **1·2단(시즌0)**을 뜻한다 —
3·4단은 시즌1이므로 지금 대기 항목이 아니다.

## 4. ★고정할 것 — 경계는 테스트로 서야 한다

경계가 코드에 이미 있으므로 위험은 "없다"가 아니라 **"조용히 사라진다"**다.
제안(코드 0줄, 승인 후 구현):

1. **[시즌0] 선택은 어떤 경우에도 원장을 건드리지 않는다.** `listMusicAssetsAction`
   호출 전후 `credit_transactions` 카운트 동일.
2. **[시즌0] 가격 미설정 = 생성 거부, 그러나 선택은 정상.** 가격 키 부재 상태에서
   `createMusicGeneration` → `music_not_priced` **이면서** 목록은 정상 반환.
   ★이 조합이 **지금 라이브 상태이고 시즌0의 의도된 상태**이므로 오늘 그대로 검증
   가능하다 — 그리고 이 테스트가 **"누가 4단을 먼저 켰다"를 잡는 그물**이 된다.
3. **[시즌1] 캡 15가 실제로 막는다.** 16번째가 `music_cap_reached`, 그 시점에도
   라이브러리 선택은 무상.
4. **[시즌0·유지] 남의 AI 곡은 목록에 없고 렌더에서도 거부된다.**
   ★**AI 행이 생기지 않는 시즌0에서도 이 테스트를 남긴다** — 코드에 살아 있는 분기가
   테스트 없이 잠들면 그게 썩는 방식이다(0절 규칙의 짝). 유닛
   `lib/music-picker-scope.test.ts`가 목록 쪽 절반을 이미 덮었다(11/11); 렌더 쪽 절반은
   행이 필요하다.

★3·4는 행을 만들어야 하므로 `e2e/i2v-reference-guard.mjs`와 같은 규율을 따른다 —
전용 e2e 유저, 끝에 삭제, 삭제 자체를 단정.

## 4b. ★★1,000곡 개정 — 7절이 1순위가 된 이유 (B안에서도 그대로)

라이브러리 **300 → 1,000곡** 확정. 이것 하나로 아래 세 항목의 순위가 바뀐다.

### (1) 7절 결함 — ★B안 단독으로도 상한에 닿는다. 수정 완료

300곡일 때 계산은 "AI 행 ~700개(캡 15 × 약 47명)부터"였다. **1,000곡은 라이브러리
단독으로 기본 상한(1000)에 정확히 닿는다.** 발동 조건이 셋으로 갈린다:

| 상태 | 결과 |
|---|---|
| 라이브러리 정확히 1,000곡 | **아직 손실 0** — 1,000행이 있고 1,000행이 온다. **경계 위** |
| ★라이브러리 1,001곡 이상 | **초과분이 조용히 사라진다** (B안 단독으로 성립) |
| ★[시즌1] 생성이 붙는 날 | `'ai' < 'library'` 정렬 때문에 **AI 행 1개만 생겨도 라이브러리가 밀려난다** |

★**그리고 경계 위에서는 정상과 절단을 구별할 수 없다** — "1,000행을 받았다"가 "1,000곡이
전부다"인지 "더 있는데 잘렸다"인지 결과만으로는 같다. **그게 명시 상한이 필요한
이유이고**, 지금은 `MUSIC_PICKER_MAX_ROWS=2000`이라 1,000곡이 `truncated=false`로
돌아오므로 그 모호함이 없다.

★즉 이 수정은 C안 때문이 아니라 **1,000이라는 수 때문에** 선행 조건이다. B안 확정으로도
유지된다.

★그래서 설계 항목이 아니라 **선행 조건**이다. 오늘 고쳤다(`lib/studio.ts` +
`lib/music-picker-scope.ts` 신설):

| 전 | 후 |
|---|---|
| `.order('source')` → `'ai'`가 먼저 → 라이브러리가 잘림 | **source 정렬 제거**, `title` 정렬 |
| `.limit()` 없음 → PostgREST 기본 상한이 조용히 자름 | **`MUSIC_PICKER_MAX_ROWS = 2000` 명시** + 도달 시 `console.error` + `truncated` 플래그 반환 |
| source/user 필터를 **JS에서** → 남의 AI 행을 전부 읽어 옴 | **SQL `or(and(...),and(...))`** — 남의 행은 Postgres가 안 준다 |
| 규칙이 필터 문자열 안에 있어 테스트가 못 봄 | **`lib/music-picker-scope.ts`로 분리**, 유닛 11/11 |

★**상한을 없애지 않고 우리 것으로 만든 이유**: 상한이 없으면 PostgREST의 상한이 쓰이고
그건 **조용하다**. 2000은 계획 카탈로그(1,000 + 캡 15)보다 위이고, 넘으면 **로그와
플래그로 드러난다.** 카탈로그가 커지면 올리는 것이지 지우는 것이 아니다.

★**SQL과 JS 두 겹을 남겨 둔 이유**: 방어 깊이인데, 두 겹이 **어긋나면** 그게 더 위험하다.
그래서 유닛 테스트가 **7가지 행 모양에서 둘의 답이 같음을 단정**하고, 런타임에는 JS가
무언가를 걸러내면(=SQL이 통과시켰다는 뜻) `console.error`로 보고한다.

★**본부 규칙 반영("판정 못 하면 무상 통과 말고 막아라")**: `active`가 **NULL인
라이브러리 행은 withheld**(truthy 검사 아님 — `=== true`), `source`가 `'library'`/`'ai'`
둘 다 아니면 **거부**. 렌더 경로도 같이 닫았다 — `resolveMusicSignature`는 두 분기를
열거만 하고 **else가 없어서** 제3의 `source` 값이 통과했다. 명시 거부를 넣었다.
★이 컬럼에 CHECK가 있는지 레포로는 증명 불가([[feedback-db-object-absence-unprovable-by-repo]])
이므로 제3값은 가설로 두지 않는다.

### (2) 격자 재설계 — 48칸은 1,000곡에서 "스크롤"이 된다

1,000 / 48 = **칸당 21곡**. 목표 = 칸당 12~13곡 → **~80칸**.

★축을 **2개로 유지하고 값을 늘린다**(3축으로 80칸을 만들지 않는다):

| 안 | 구성 | 칸 | 칸당 | 판정 |
|---|---|---|---|---|
| **권고** | `genre` 10 × `mood` 8 | **80** | **12.5** | 필터 칩 18개, 교차 조건 2개 |
| 대안 | `genre` 8 × `mood` 5 × `tempo` 2 | 80 | 12.5 | 칩 15개인데 **교차 조건 3개** |

★**3축을 권고하지 않는 이유는 칸 수가 아니라 희소성이다.** 칸 총수는 같지만 3축 칸은
조건 3개의 교집합이라 실제 카탈로그에서 **빈 칸이 훨씬 많이 생긴다**(예: "triumphant ×
ambient × fast"). 빈 칸은 필터를 눌렀는데 아무것도 안 나오는 화면이고, 그건 1,000곡을
만든 이유를 지운다. `tempo`는 08-02 판단 그대로 **격자 축이 아니라 필터**로 남긴다.

★**축의 값(어떤 장르·어떤 무드 10개/8개)은 여전히 제니3·본부 대기.** 여기서 정하는 것은
**칸 수와 축 개수**뿐이다. 5절의 17개 값은 **8×6 시절의 예시**이고 그 중립성 기준
(제품군·업종·광고형식 0개)만 그대로 승계한다.

### (3) ★자동 1차 선별 = 필수. 근거를 숫자로

제니2 산식: 1,000곡 × 40초 = **11시간**, 채택률 1/3이면 3,000곡 = **33시간**. 대체 불가.

**측정한 것 (오늘, 실제 오디오로)**

기계 심사 1회 = `ffmpeg -af ebur128=peak=true,astats` **한 패스**. 40초 파일 3회 실행:

```
run1 1,596 ms   run2 2,265 ms   run3 1,734 ms      (중위 ~1.7 s/곡)
디코드만 (필터 없음) 400 ms  ← 프로세스 시작 하한
```

→ **1,000곡 ≈ 28분 / 3,000곡 ≈ 85분**(단일 스레드). 4병렬이면 7분 / 21분.
**즉 심사 비용은 사람 시간 대비 무시할 수 있다** — 이건 "돌릴까 말까"의 문제가 아니다.

**그 한 패스가 실제로 내놓는 판정 가능한 값** (같은 실행에서 채집):

```
Integrated loudness  I: -30.7 LUFS      Loudness range LRA: 18.1 LU
True peak            -15.8 dBFS         DC offset -0.000112
RMS level            -36.2 dB           Flat factor 0.000000
Peak count 8 / Abs peak count 4         Noise floor -68.7 dB
```

기계적으로 거를 수 있는 것 = **길이 규격 이탈 / 클리핑(true peak ≥ -1 dBFS) / 과소·과대
라우드니스 / 앞뒤 무음 과다 / DC offset / 모노-스테레오·샘플레이트 불일치 / 완전 무음 ·
플랫 구간 / 바이트 동일 중복(content hash, 적재기에 이미 있음)**.

★**정직한 한계 — 채택률은 지금 낼 수 없다.** `studio_music_assets` **0행**이고 벤더도
미확정이다. 위 값은 **샘플 1개**(⑪B 영상의 AAC 트랙)에서 나온 것이고 음악 벤더 출력이
아니다. **"기준이 몇 %를 거른다"를 지금 적으면 그게 출처 없는 수치다**
([[feedback-work-style]]). 대신:

- **교정 절차**: 첫 배치 **50~100곡**에 심사를 돌려 **기준별 적발률을 측정**하고, 그
  숫자로 3,000이라는 발주량을 다시 계산한다. **1/3이라는 채택률 자체가 아직 미검증
  가정**이고, 33시간을 만드는 것이 바로 그 가정이다.
- ★**그리고 지배항은 채택률이 아니라 "곡당 몇 초를 듣는가"다.** 40초를 끝까지 듣는 것은
  기각에 필요하지 않다:

| | 곡당 | 3,000곡 |
|---|---|---|
| 전곡 청취 | 40 s | **33.3 h** |
| **가장 큰 구간 8초 오디션** | 8 s | **6.7 h** |
| + 기계 심사가 R% 사전 기각 | 8 s × (1−R) | R=20%면 **5.3 h** |

→ **오디션 길이를 줄이는 것이 어떤 필터보다 큰 레버다.** 그리고 심사는 기각뿐 아니라
**정렬**을 준다 — 점수 내림차순으로 듣고 1,000곡이 차면 멈추면, 3,000곡을 다 듣지 않는다.

**그래서 파이프라인 우선순위 변경**: `[3] 큐레이션`이 "범위 미정(대표님)"에서
**`[2.5] 기계 심사 + 정렬` = 발사 필수**로 올라간다. 6절 갱신 참조.

### (4) 비용 갱신

생성 원가 **$150~450** / Full Ownership이면 **$1,050**. (계약 형태는 대표님·본부·고문)

## 5. 격자 값 — 범용, 중립어 (칸 수는 4b-(2)가 갱신)

본부 확정: 시즌명·테마와 **무관하게** 착수 가능. 금지: **화장품·코스메틱·CF용** 등
제품군·업종·광고형식 어휘. → 무드·장르 중립어만.
(같은 규칙을 코드에 대해 강제하는 체크가 이미 있다: `npm run test:theme-leak`.)

**축 구조 = 4b-(2) 확정분: `genre` 10 × `mood` 8 = 80칸, `tempo`는 필터.**

아래는 **8×6 시절의 예시 값**이고, 참고용으로만 남긴다 — **값은 제니3·본부 대기**이고
10개/8개로 늘어난다. 승계되는 것은 **중립성 기준**뿐이다.

| 축 | 예시 값 (참고, 미확정) | 당시 개수 |
|---|---|---|
| `genre` | ambient / cinematic / orchestral / electronic / acoustic / pop / hip-hop / rock | 8 → **10 필요** |
| `mood` | calm / warm / bright / tense / melancholy / triumphant | 6 → **8 필요** |
| `tempo` | slow(<90) / mid(90–120) / fast(>120) | 3 (격자 축 아님) |

★중립성 자체 점검: 위 17개 값 중 제품군·업종·광고형식 어휘 **0개**. 값이 늘어날 때도
같은 기준이고, 코드 쪽은 `npm run test:theme-leak`가 강제한다.

**08-02 §2의 A/B 결정 — 이제 A로 확정 가능하다.** 그 문서가 A를 못 고른 이유는
"축을 모르고 컬럼을 만들면 설명할 수 없는 상수"였고, **축이 정해졌으므로 그 반대
사유가 사라졌다.** 필요한 컬럼: `genre` TEXT · `bpm` INT · `sort_order` INT
(`mood`는 이미 있다).
★**마이그레이션 SQL은 내가 만들지 않는다(⑥)** — 컬럼 목록만 여기 남기고 본체가 쓴다.
그리고 [[feedback-migration-before-code-push]] 순서: **마이그 Run → 코드 push.**

★`mood`가 지금 **표시 문자열과 분류 키를 겸한다**(`{mood} — {title}`). 격자가 들어오면
그 겹침을 끊어야 한다 — 표시는 `title`, 분류는 축 컬럼.

## 6. 파이프라인 — 생성 경로의 자리

```
[0]   매니페스트       곡 목록 + id + 배치 라이선스        ← 격자 값 확정 후 착수 가능
[1]   배치 적재        업로드→해시→v1m→upsert            ← ✅ 완료 (seed:music:batch)
[2]   프로버넌스       배치 단위 4컬럼                     ← ✅ 골격, 값은 계약 대기
[2.5] ★기계 심사+정렬  ebur128/astats 한 패스 → 기각 + 점수 ← ★발사 필수 (4b-(3))
[3]   큐레이션         active on/off + 심사 점수순 목록     ← [2.5]에 얹힘
[4]   피커             필터·미리듣기·페이로드              ← 4-3 ✅ / 7절 ✅ / 4-1,2 격자 대기
──────────────────────────────────────────────────────────
[1'] ★[시즌1] 생성 경로  프롬프트→가격·캡·잔액→워커 music 레인→R2→v1m→같은 테이블
```

★`[2.5]`가 1,000곡 확정으로 새로 필수가 된 단계다. 곡당 ~1.7초, 3,000곡 85분(단일
스레드) — **기계 비용이 무시할 수준이라 "돌릴까"가 아니라 "무엇으로 정렬하나"가 질문**이다.
그리고 `[3]` 큐레이션은 독립 화면이 아니라 **`[2.5]`의 출력(점수순 목록) 위에 active
토글을 올린 것**이 된다. 08-02에서 "범위 미정"이던 것이 여기서 좁혀진다.

★`[1']`는 `[1]`의 형제다 — **같은 테이블, 같은 v1m, 같은 피커**로 합류하고 다른 것은
`source`와 **누가 소유하는가**뿐이다. 그래서 4절 테스트가 두 경로 공통 계약이 된다.
★워커 music 레인은 이미 있다(③a). C안은 그것을 **켜는** 것이지 만드는 것이 아니다.

## 7. ★조용한 오작동 1건 — 진단 기록 (수정 완료, 상세는 4b-(1))

★**아래는 고치기 전의 진단 기록이다.** 1,000곡 확정으로 이것이 **선행 조건**이 되어
2026-08-07에 수정했다 — 조치 내역은 **4b-(1)** 표. 진단문을 남겨 두는 이유는 "왜 B안에서
무해했는지"가 다음에 같은 판단을 할 때 필요하기 때문이다.

`listMusicAssets`는 **고치기 전에** 이렇게 조회했다:

```
.eq('status','ready').not('url','is',null)
.order('source', { ascending: true })      ← 'ai' < 'library'
...그리고 source/user 필터는 SQL이 아니라 JS에서 적용된다(:1341)
```

**B안에서는 무해했다** — AI 행이 0이었다. **C안에서는 아니다.**

1. **`.limit()`이 없다.** PostgREST 기본 상한(Supabase `db-max-rows`, 통상 **1000**)이
   걸린다.
2. **정렬이 `source` 오름차순**이라 `'ai'`가 먼저 온다.
3. → 총 ready 행이 상한을 넘는 순간 **잘려 나가는 쪽이 `library`다.**

즉 시즌이 채워질수록 **참가자 피커에서 라이브러리 곡이 조용히 줄어든다.** 에러도 경고도
없다. 부수적으로, 참가자 한 명의 피커 조회가 **다른 참가자들의 AI 행 전부를 읽어 온다**
(반환 전에 걸러지므로 유출은 아니지만, 500명×15 = 7,500행 + 카탈로그).

**발동 시점이 카탈로그 크기에 달려 있었다** — 그리고 그것이 이 항목의 순위를 바꿨다:

| 카탈로그 | 언제부터 곡이 사라지나 |
|---|---|
| 300곡 (구 계획) | AI 행 ~700개 = 캡 15 기준 **약 47명**이 다 쓴 뒤 |
| **1,000곡 (확정)** | **라이브러리 단독으로 상한** → **첫 생성 1건부터** |

★**단정하지 않는 것**: Supabase 프로젝트의 실제 `db-max-rows`를 나는 못 읽었다(대시보드
설정). 1000은 기본값이다. **상한이 무엇이든 "AI가 먼저 정렬되고 라이브러리가 잘린다"는
순서는 값과 무관하게 성립한다** — 그게 이 항목의 요지였고, 1,000곡은 그 순서를 **어떤
상한에서도 도달 가능하게** 만든다. 그래서 상한을 추측하지 않고 **우리 상한을 명시**하는
쪽으로 고쳤다(4b-(1)).
