## 0. 경계의 한 줄 원칙
- **광고부는 광고주·계약·캠페인·소재·정산의 업무 데이터를 소유한다. 본부는 "누구에게, 어디에, 광고를 보여도 되는가"의 판정과 그 증거(권한·동의·연령·승인·감사 로그)를 소유한다.**
- 두 영역은 **서버 함수 계약**(§3)과 **service_role 전용 테이블**(§2)로만 만난다. 브라우저가 DB 테이블을 직접 읽고 쓰는 경로는 만들지 않는다.

## 2. 데이터 소유 경계와 필수 보안 규칙

### 2-1. 소유
- **본부 소유(공통):** `profiles`, 멤버십·결제 관련 테이블, `platform_config`, (신설 제안) 광고 슬롯 레지스트리·광고 제거 권한·광고 송출/감사 로그.
- **광고부 소유(업무):** 광고주, 계약, 캠페인, 소재, 청구·정산 기록. [제안] 같은 DB의 별도 테이블 묶음(접두사 `ads_`)으로 시작. 별도 DB·저장소 분리는 계획서가 미정으로 둠 [미정].

### 2-2. 모든 신규 테이블에 적용하는 규칙 (10-16에 이 레포가 실제로 겪은 구멍에서 나온 것)

2. **"내 행만 UPDATE" 정책 금지.** [레포] `profiles_own_update`가 테이블 권한과 합쳐져 사용자가 자기 `role`을 `admin`으로 바꿀 수 있는 구멍이 되었다(10-16 잠금, `reports/profiles_lockdown_2026-10-16.sql`).
3. **`INSERT ... check (true)` 정책 금지.** [레포] `genesis_applications`의 "anyone can apply"가 서버 검증을 우회하는 구멍이었다(`reports/applications_lockdown_2026-10-16.sql`, 적용 여부는 TK님 확인 중).
4. **컬럼 기본값에 "공개/승인" 상태를 두지 않는다.** [레포] `moderation_status DEFAULT 'approved'`(`watch_safety_2026-06.sql:36`)가 위 구멍을 더 위험하게 만들었다. 광고 소재·슬롯의 기본 상태는 `pending`/`draft`로 한다.
5. **새 테이블마다 `check_service_role_grants()`가 0행**이어야 한다(`deploy:prod` 게이트가 이미 이 검사를 한다). 그리고 `reports/db_write_surface_audit_2026-10-16.sql`을 돌려 anon/authenticated 쓰기 면이 0임을 확인한다.
6. 관리자 판정은 `is_admin()`/`requireAdmin()`이 `profiles.role`을 읽는 구조 [레포]. 광고 권한을 여기에 얹을 때도 `profiles` 쓰기 경로는 service_role만 유지한다.
7. DB 마이그레이션은 `reports/`에 ASCII 전용 SQL 파일로 쓰고 TK님이 Run한다(블록 하나 = 쿼리 하나, 되돌리기 블록은 별도 파일 또는 하단 분리).

## 3. 권한 판정 계약 (광고 제거 + 노출 자격)

### 3-1. 현재 구조 [레포]
- 멤버십은 `profiles.membership_tier`(`general|creator`) 하나, 만료는 읽는 시점에 `membership_expires_at`로 판정(`lib/membership.ts`). 파트너는 직교 축(`partner_tier`). 가격은 `platform_config`의 `membership_creator_price_usd` 하나, Stripe 구독도 단일 상품(`lib/membership-billing.ts`).
- 따라서 계획서의 "통합 $19.99 / 사업부 패스 $6.99" 두 상품은 **현재 구조로 표현되지 않는다.** 기존 `creator` 구독이 "통합 $19.99"인지도 확인되지 않음 [미정, TK님].

### 3-2. 제안: 광고 제거 권한을 파생 값으로
- 신설 테이블 [제안] `ad_free_entitlements(id, user_id, scope, source, starts_at, expires_at, created_at)`
  - `scope`: `all` 또는 사업부 ID(`PageId` 중 하나, 예: `games`). 사업부 ID 목록은 `lib/site-nav.ts`의 `PageId`와 한 곳에서 동기화한다 [레포: `home|tournament|entertainment|daily|market|education|jobs|games`].
  - `source`: `membership_integrated` | `division_pass` | `grant`(관리자 부여).
  - 쓰기는 결제 웹훅과 관리자 서버 액션(service_role)만. 클라이언트 쓰기 없음(§2-2).
- 통합 멤버십은 별도 행을 만들지 않고 "`membership` 활성이면 `scope=all`"로 **판정 시점에 파생**하는 방안과, 결제 시 행을 만들어 두는 방안이 있다. [제안] 후자(행을 만든다). 이유: 만료·환불·수동 부여를 한 테이블에서 감사할 수 있고, 멤버십 로직(`lib/membership.ts`)을 광고 쪽 요구로 건드리지 않는다.
- 기존 멤버십·결제와의 충돌 방지: 광고 제거 권한은 `membership_events` 웹훅 처리의 **후속 단계**로 갱신하되, 웹훅 핸들러 자체의 멱등 구조(event.id PK)는 바꾸지 않는다 [레포: `app/api/membership/stripe-webhook/route.ts`].

### 3-3. 판정 함수 계약 [제안]
서버 전용 함수 하나가 모든 슬롯의 노출 가능 여부를 결정한다. 입력과 출력만 합의하고 내부 구현은 본부 소유.

```
입력: { userId | null, division, slotKey, routePath, consentState, ageState, locale }
출력: { show: boolean, reason: string, personalization: 'none' | 'allowed', creativeSource: 'direct' | 'network' | null }
```
- `reason` 값은 열거형 고정(예: `ok`, `ad_free`, `slot_not_approved`, `protected_zone`, `no_consent`, `age_unknown`, `error`).
- **실패 시 항상 `show:false`** (fail closed). 판정 오류가 광고 노출로 이어지면 안 된다. [레포] 이 코드베이스의 기존 게이트(`lib/watch-gate.ts`, `watch-visibility.ts`)도 fail-closed 규칙을 쓴다.
- 클라이언트는 `show`와 `personalization`만 받는다. 프로필 컬럼, 멤버십 상태, 연령 값은 클라이언트로 내려가지 않는다.
- 광고 제거 대상 형식: 계획서 §2.2에 따라 네트워크 배너, 직접 판매 디스플레이, 재생 전 광고. 서비스 자체의 상업적 콘텐츠(Market 광고 상품, Jobs 유료 공고, 협찬)는 별도 정책이 정해질 때까지 이 함수의 대상에서 **제외**한다 [미정].

## 4. 광고 슬롯 레지스트리와 승인

### 4-1. 레지스트리 [제안]
신설 테이블 `ad_slots(id, division, slot_key, format, protected_zone_ok, status, approved_by_division, approved_at, approved_note, created_at, updated_at)`
- `division`: `PageId` 값. `status`: `draft` → `proposed` → `approved` → `paused`. **기본값 `draft`.**
- `approved_*`는 **사업부 제니의 승인 기록**이다. 승인 주체를 이 레포의 로그인 사용자(`profiles`)와 어떻게 연결할지는 [미정]: 사업부 제니는 사람 계정이 아니므로, TK님이 승인한 사실을 관리자가 입력하는 방식인지, 사업부별 담당 관리자 계정을 두는지 결정 필요.
- 슬롯 변경은 항상 이력으로 남긴다(누가·언제·이전 값). 계획서 §1 "사업부 승인 없이 위치 추가·변경 금지"를 시스템이 강제하려면 `approved` 상태 슬롯의 `division`/`slot_key`/`format` 변경이 **새 승인 요청**으로 되돌아가야 한다.

### 4-2. 보호 영역은 코드로 금지 (계획서 §3 표)
- 보호 영역은 설정값이 아니라 **허용 목록 방식**으로 막는다: 광고 슬롯 컴포넌트는 사업부 승인된 슬롯이 있는 **특정 경로 패턴에서만** 렌더되고, 그 외 모든 경로(기본값)는 광고 없음.
- 어떤 설정으로도 광고가 올라가면 안 되는 **전역 금지 경로** [제안]: 로그인·가입·결제·설정·`/profile`·`/apply`·`/studio` 편집기·`/admin/**`·`/welcome/**`·인증 콜백. 인증 쿠키가 같은 도메인이고 제3자 스크립트가 쿠키·DOM에 접근할 수 있기 때문이다.
- 사업부별 보호 영역(계획서 표): Games 실제 대국 중 / Entertainment·Daily 영상·뉴스 본문 중간 / Tournament 출품작 재생 중·투표 / Market 결제·독립 검증 결과 / Jobs 지원서 작성 / Education 강의 진행 중. 각 항목은 [미정]이 아니라 이미 계획서 확정이지만, **어느 경로·컴포넌트가 "재생 중/진행 중"인지**는 사업부가 정의해 슬롯 레지스트리 허용 경로로 환산해야 한다.
- [미정] Tournament의 "Watch 목록" 광고 허용이 대회 공정성 원칙과 충돌하지 않는지는 Tournament 담당 판단.

## 5. 송출 계층 (Delivery)

- **위치:** 공통 틀 `app/_site/SiteFrame.tsx`에 슬롯 컴포넌트를 둔다 [레포 확인: 현재 광고 스크립트·태그 전무, `next.config.ts`는 빈 설정, 레포에서 CSP 헤더를 찾지 못함 -- `vercel.json` 후반부는 확인 못 함].
- **서버가 판정, 클라이언트는 실행만:** 서버가 §3-3 함수로 `show`를 정한 뒤 슬롯 컴포넌트를 렌더하고, 클라이언트는 `show=true`일 때만 태그(GAM/AdSense) 또는 직접 판매 소재를 로드한다. 클라이언트 쪽 판정은 우회가 쉬워 금지.
- **직접 판매 소재는 1st-party(OXXOVO R2)에서 제공**하고, 네트워크 태그와 별도 컴포넌트로 둔다. OXXOVO 자체 광고 데이터·계약 기록은 외부 네트워크에 종속되지 않는다는 계획서 §2.1을 따른다.
- **CSP:** 광고 스크립트를 올리기 전에 CSP를 설계·적용해야 한다 [제안, 광고 도입 선행조건]. 허용 도메인 최소화, 광고 허용 경로와 금지 경로의 헤더 분리.
- **성능·안정성:** 광고 로딩 실패가 페이지를 깨지 않도록 격리하고(고정 영역 확보, 지연 로드), 광고 때문에 핵심 지표가 나빠지는지 측정 지표를 먼저 정한다 [미정: 현재 측정 체계 없음].
- **Google 연결(GAM·AdSense):** 본부가 연결 계층을 소유하되 계정 승인·네트워크 정책·재고 자격 확인 후에만, TK님 승인 후에만 연결. 네트워크 카테고리 차단만으로 완벽한 차단을 가정하지 않는다(계획서 §6).

## 6. 동의·연령·개인정보 (본부 소유, 송출 선행조건)

현재 상태 [레포]:
- 쿠키 동의 배너·저장 코드 없음. 개인정보 처리방침 §5에 쿠키 설명 한 문단뿐, 광고·추적·광고 파트너 고지 없음(`app/privacy/page.tsx`).
- 약관: 13세 이상, 18세 미만은 부모 동의(`app/terms/page.tsx`). 생년월일·연령 컬럼 없음(`profiles` 컬럼 목록 기준). **따라서 모든 사용자가 "연령 미확인"이다.**

계약 [제안]:
- 연령 상태: `unknown | under_18 | adult`. 현재 값은 전원 `unknown`.
- 계획서 §6에 따라 **연령 미확인·18세 미만은 비개인화 광고가 기본.** 판정 함수는 `ageState`가 `adult`로 확인되지 않으면 `personalization:'none'`을 반환한다.
- 동의 상태: `unset | necessary_only | ads_ok`(최소). 비로그인 방문자도 대상이므로 계정이 아니라 **브라우저·지역 단위 동의**가 필요하다. CMP 도입 또는 자체 동의 저장은 [미정], 법무 검토 후 결정(지역별 규칙은 지수의 판단 영역이 아님).
- 처리방침·약관에 광고, 광고 파트너 정보 제공, 미성년자 보호를 반영하는 문구는 **사용자 대면 문안이므로 제니3 확정본이 필요**하다(지수가 쓰지 않는다).

## 7. 로그와 감사

- **송출 기록** [제안]: 슬롯·캠페인·소재·시각·판정 결과(`reason`)·(비식별) 사용자 구분. 노출 단위 로그는 양이 많고 개인정보 부담이 있으므로 **기록 수준(노출 단위 vs 집계)을 먼저 결정** [미정]. 정산 근거와 개인정보 최소화의 균형이 기준.
- **승인·변경 감사** [제안]: 슬롯 승인, 캠페인 중단·재개, 소재 심사 결과, 권한 부여는 누가·언제·이전 값·사유를 append-only로 남긴다. [레포 교훈] `updated_at` 트리거만으로는 변경 시점을 알 수 없고(`profiles`는 아무 UPDATE에나 갱신됨), 이력 테이블이 없으면 사고 때 "언제 바뀌었는지" 증명이 불가능했다.
- 스키마·보관 기간·접근 권한은 본부 소유. 광고부는 기록을 요구하고 조회 화면을 쓴다.

## 8. 공통 Admin 접근권한

- 현재 [레포]: 관리자는 `profiles.role`(`user|admin`) 하나, 매니저 확장 `is_staff()`는 DB에 마이그레이션이 이미 있음(본문 미확인). 가드는 `requireAdmin()`.
- 광고부 담당자가 광고 데이터만 보게 하려면 현재의 2단계 역할로 부족하다 [제안]: `profiles.role`을 늘리지 말고 **별도 권한 테이블**(`admin_scopes(user_id, scope)`, 예: `ads`)을 두고 `requireAdminScope('ads')` 같은 가드를 추가. 이유: `profiles.role`은 `is_admin()`이 읽는 보안 핵심이고, 10-16에 잠금 작업을 마친 컬럼이므로 용도를 늘리지 않는다.
- 권한 테이블 쓰기는 service_role만(§2-2).
- AMS 화면 위치(`/admin/ads/**` 등)와 공통 Admin 내비게이션 항목 추가는 본부 승인 대상 파일을 건드린다(§10).

## 9. 결제·청구·정산

- 재사용 가능 [레포]: Stripe 연동, 웹훅 멱등 패턴(`membership_events`), 이메일 발송, 크론.
- 없음 [레포]: B2B 청구서, 계약서 보관, 광고주 계정, 정산·세금. 개인 결제·구독 용도만 있음.
- [제안] 광고주 청구는 **멤버십 웹훅과 분리된 엔드포인트와 이벤트 테이블**로 설계(Stripe Invoicing 등 방식은 [미정]). 멤버십 결제 흐름에 광고주 이벤트를 섞지 않는다: 둘이 같은 `event.id` 처리 경로를 공유하면 한쪽 장애·변경이 다른 쪽 수익에 영향을 준다.
- 광고 제거 결제(통합·사업부 패스)는 사용자 결제이므로 **본부(멤버십·결제) 소유**. 광고부는 이 결제에 관여하지 않는다.
- 광고 제작비와 게재비를 구분해 계약·정산한다는 계획서 §4-C는 데이터 모델에서 **제작 계약과 송출 계약을 별개 레코드**로 두는 것으로 반영한다.
