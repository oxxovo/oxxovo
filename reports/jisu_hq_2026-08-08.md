## ② failed 처리 — 3문 답변

**근거 범위**: `oxxovo-scoring/src/{batch,recommendations}.ts` 전문 + `oxxovo/lib/awards-gate.ts` +
`app/admin/applications/actions.ts` 전문 읽음. DB 는 `scoring_results` 전 행 조회
(현재 failed 0건 / in_progress 0건, season_test 51건 전부 completed).
Railway 실행 로그는 **못 봤다** — 아래 ⓐ의 "크론 틱 간" 은 코드 구조에서 나온 것이지 로그에서 나온 게 아니다.

### ⓐ MAX_RETRIES 3회는 **크론 틱 간**이다. 한 실행 안이 아니다.

`batch.ts:430` 의 배치 루프는 `pickPending` → `processOne` 을 `BATCH_SIZE` 만큼 도는데,
**실패한 행을 그 루프 안에서 다시 잡지 않는다.** `processOne` 의 catch 는
`handleFailure` 를 부르고 그대로 다음 반복으로 간다. 재시도 카운터
(`scoring_results.processing_attempts`)는 DB 에 있고 `startScoringRow` 가 **잡을 때마다 +1** 한다.

→ 한 틱에 한 행은 **최대 1회** 시도된다. 3회를 채우려면 **크론이 3번 돌아야** 한다.
크론이 `0 * * * *`(시간당 1회)이므로 **소진까지 최소 2시간**이 걸린다.

★부수 효과 하나: `BATCH_SIZE` 가 충분히 크면 같은 틱 안에서 같은 행을 다시 만날 수는 있다.
예선은 `handleFailure` 가 status 를 `pending` 으로 되돌리므로 후보에 다시 들어오고,
`pickPending` 의 skip 집합은 `failed && attempts>=3` 만 빼기 때문이다. 즉
**"틱 간" 이 설계 의도이고, "한 틱 안 3회" 도 BATCH_SIZE 에 따라 실제로 일어난다.**
이건 어느 쪽이 맞냐의 문제가 아니라 **의도된 상한이 두 축에 걸쳐 있다**는 뜻이고,
현재 값(`BATCH_SIZE=30`, 500편)에서는 사실상 틱 간이다.

### ⓑ 그렇다. 다음 틱이 다시 집는다 — **소진 전까지는.**

`pickPending` 의 제외 집합 (`batch.ts:131-136`):

```
done      = judged_status IN ('completed','in_progress')
exhausted = judged_status = 'failed' AND processing_attempts >= MAX_RETRIES
```

`failed` 인데 `attempts < 3` 이면 **어느 집합에도 안 들어간다** → 후보로 남는다.
예선은 status 가 `pending` 으로 복구돼 있어 후보 쿼리에도 걸리고, 본선은 status 불변
(`main_round_submitted`)이라 애초에 계속 후보다. **의도대로 동작한다.**

★**단 여기서 진짜 함정이 하나 나왔다 — `in_progress` 는 영구 제외다.**
`done` 집합이 `in_progress` 를 포함한다. 워커가 `startScoringRow` 로 `in_progress` 를 찍은 뒤
**프로세스가 죽으면**(OOM, Railway 재시작, 컨테이너 교체) `handleFailure` 가 안 돌아서
행이 `in_progress` 로 남는다. 그러면 그 행은 **영원히 skip 된다** — 재시도 소진도 아니고
실패도 아니라서 어떤 카운터에도 안 잡힌다. `countUnfinished` 는 `status='verifying'` 을
미완으로 세므로 예선은 Top N 확정이 **영구 보류**된다(사람이 알아채긴 한다).
**본선은 status 가 안 바뀌므로 그 보호도 없다.**
현재 실측 `in_progress` 0건이라 지금 당장은 없다. 500편 10.6시간 주행에서 워커가
한 번이라도 죽으면 생긴다. **lease/타임아웃이 없다** — 별건 큐로 올린다.

### ⓒ ★본부 전제 하나가 틀렸다. 그리고 진짜 구멍은 다른 데 있다.

> "어워드 게이트 2번은 scoredCount === submittedCount 를 본다. 즉 failed 가 몇 건 있어도 시즌이 확정되나."

**아니다. failed 가 있으면 어워드 게이트는 막는다.** `scoredCount` 는
"scoring_results 행 수" 가 아니라 **`judged_status='completed'` 인 행 수**다
(`app/admin/applications/actions.ts:417`):

```ts
const scoredCount = (scoringRes.data ?? []).filter(
  (s) => s.judged_status === 'completed' && submittedSet.has(s.application_id),
).length
```

failed 는 completed 가 아니므로 `scoredCount < submittedCount` 가 되고
`lib/awards-gate.ts:134` 가 `scoring_incomplete` 로 차단한다. 500편 중 1건만 failed 여도
**시상 승인 버튼이 안 눌린다.** fail-closed 가 작동한다.

★**대신 본부가 가리킨 그 병리는 실재한다. 위치가 어워드가 아니라 예선 Top N 이다.**

`recommendations.ts` 의 확정 경로:

| 검사 | 무엇을 세나 | failed 를 어떻게 다루나 |
|---|---|---|
| `countUnfinished` | status pending/verifying | **소진분(failed+attempts>=3)을 "끝난 것"으로 센다** (l.24 주석에 명시) |
| `countUndeliverable` | 영상 URL 이 null 인 행 | failed 는 **URL 이 있다** → 안 걸린다 |
| Top N 산출 | `judged_status='completed'` + `integrity_flag=false` | failed 는 **그냥 빠진다** |

세 개가 전부 통과한다 → **Top N 이 확정된다.** 그리고 확정은 `season_recommendations`
행 존재가 marker 라 **1회성이고 되돌릴 수 없다.**

즉 본부 문장을 정확한 자리에 옮기면 이렇게 된다:

> **500편 중 failed 가 몇 건이든 예선 Top N 은 확정되고, 그 참가자들은
> 점수 없이 순위에서 빠진 채로 시즌이 넘어간다.**

★**다만 조용하지는 않다.** `sendAdminEmail` 이 확정 메일에
`미채점 오류: N건 (시스템 오류 — 사용자 탈락 아님, 수동 검토 대상)` 을 넣는다
(`countExhaustedFailed`). 그래서 **차단은 안 하지만 보고는 한다.**
그리고 `top.length === 0` 이면 확정하지 않고 별도 메일을 보낸다.

**그래서 이건 버그가 아니라 정책 선택이다.** 그리고 나는 그 선택이 지금 상태로 **불완전**하다고 본다:

- 지금은 **0건이면 멈추고, 1건이든 499건이든 통과**한다. 문턱이 0 하나뿐이다.
- 참가자 손해는 "몇 명이 빠졌나" 가 아니라 **"빠진 사람이 Top N 밖이었는가"** 로 결정된다.
  실패한 행은 점수가 없으니 그걸 알 방법이 없다. 그래서 **실패 건수가 Top N 경계 근처면
  확정 자체가 근거 없는 확정**이 된다.

**제안 (승인 사안, 코드 안 건드림)**: `countUndeliverable` 옆에 대칭으로
`countExhaustedFailed > 0 이면 보류 + 어드민 메일` 을 넣는다. 이미
`sendUndeliverableAlert` 와 똑같은 모양이고, 판단 근거도 같다 —
**"부분 코호트로 1회성 확정을 하지 않는다."** 자동 타임아웃을 안 넣은 것과 같은 이유다.
지금 미착지는 막고 미채점은 안 막는데, **참가자 입장에서 둘은 구분이 안 된다.**
본부 승인 주면 다음 창에서 넣는다.

## ④ Resend — 실측 + 스로틀 설계

### 실측 (2026-08-08, 실제 계정 키, 메일 0통 발송)

`GET /domains` 로 헤더를 읽고, 이어서 `POST /emails` 를 **의도적으로 잘못된 본문**
(`to` 누락 → 422 `missing_required_field`, 발송 이전 단계에서 거부)으로 14회 연타했다.

```
ratelimit-policy = 10;w=1      <- 1초 창에 10건
ratelimit-limit  = 10
14회 연타 중 429  = 0건
회당 지연        = 118 ~ 524ms (1회 3922ms 스파이크)
검증 도메인      = oxxovo.ai (verified), oxxovo.com (verified), us-east-1
```

Resend 문서와도 일치한다: **팀당 10 req/s**, 엔드포인트·플랜 무관, 신뢰 발신자는 상향 요청 가능.
★**일당·월당 상한은 API 로 알 수 없다.** 문서에도 초당 상한만 있고, 월 쿼터는 플랜 값이라
**대시보드(resend.com/settings/usage)에서 TK님이 확인하셔야 한다.** 내가 못 보는 범위다.

### ★그런데 지금 코드는 450통을 한 번에 쏘지 않는다.

`dispatchBatch`(`app/api/cron/email-tick/route.ts:766`)는 **완전 순차**다:

```ts
for (const row of rows) {
  const verdict = await canSend(row.id, template, reminderHour)  // DB 왕복
  if (!verdict.ok) { skipped++; continue }
  const result = await send(row)                                  // Resend 왕복 + 로그 insert
}
```

`Promise.all` 이 없다. 그리고 한 통당 왕복을 **코드에서 세어보면 5회**다:

| # | 무엇 | 어디 |
|---|---|---|
| 1 | `alreadySent` SELECT | `canSend` → `log.ts:124` |
| 2 | 과거 실패행 SELECT (백오프 판정) | `canSend` → `log.ts:129` |
| 3 | ★`alreadySent` **또 한 번** | `executeSend` → `send.tsx:138` |
| 4 | Resend POST | `send.tsx:158` |
| 5 | `email_logs` INSERT | `logEmail` → `log.ts:52` |

Resend 왕복 실측 130~350ms(스파이크 3.9초 1회), Supabase 왕복 실측 중앙값 105ms
(★내 로컬에서 잰 값이다. Vercel 은 DB 와 같은 리전이라 **이건 상한**이다).
→ Resend 만 보면 실효 **초당 2~3통**이고, **10 req/s 상한에 안 닿는다.**
순차 루프가 우연히 스로틀 역할을 하고 있다.

★그래서 "스로틀이 없다" 는 지수2A 보고는 코드로는 맞지만, **레이트리밋 사고는 여기서 안 난다.**

★그리고 #3 은 **중복이다.** `canSend` 가 이미 같은 질문을 했다. 한 통당 왕복 하나,
450통이면 왕복 450회를 쓸데없이 쓴다. 아래 300초 예산에서 이게 그냥 낭비가 아니다.

### ★진짜 위험은 이쪽이다 — 300초

`export const maxDuration = 300` (route.ts:62), 크론은 `*/15 * * * *`.

통당 = DB 4회 + Resend 1회 + React 이메일 `render()` 1회.
Vercel↔Supabase 를 낙관적으로 30ms 로 잡아도 통당 **0.35~0.5초**,
내 실측 105ms 를 쓰면 통당 **0.65~0.85초**.

```
450통 × 0.4초 = 180초   (낙관)
450통 × 0.7초 = 315초   (내 실측 기준)  <- 300초를 넘는다
```

★**즉 여유가 없다.** 그리고 같은 틱이 `main_round_start` / `submission_deadline` /
`results_announced` / `selected_top50` / `not_selected` 를 **전부 순차로** 돈다.
11/8 12:00 틱은 `selected_top50` + `not_selected` 합계가 450통이다.
**넘을 가능성이 안 넘을 가능성보다 크다고 본다.**

**넘으면 어떻게 되나** — 코드를 읽고 확인했다. 함수가 중간에 죽는다.
이미 보낸 통은 `logEmail(status:'sent')` 로 남아 다음 틱 `canSend` 가 `already_sent` 로
거르므로 **중복 발송은 안 난다.** 15분 뒤 나머지가 나간다.
즉 **최악이 "일부가 15분 늦게 도착"** 이다. 데이터 손상 없음.

★단 경계에 한 통이 있다: Resend 왕복(#4)은 끝났는데 로그 INSERT(#5) 전에 죽으면
그 통은 기록이 없어 다음 틱에 **재발송**된다. 450통 중 최대 1통, 문면이 같은
결과 안내라 참가자 피해는 없다고 판단한다.

★**429 를 받으면 지금 무슨 일이 나는지도 확인했다 — 이쪽이 더 나쁘다.**
`resend.emails.send` 가 429 를 `{error}` 로 돌려주고 `executeSend` 는 그것을
`email_logs.status='failed'` 로 적는다(`send.tsx:165`). 그러면 `canSend` 의
백오프가 걸린다: **15분 → 30분 → 60분 → 120분, 5회 실패하면 `gave_up`.**
즉 429 가 연속으로 나면 그 참가자들은 **점점 뒤로 밀리다 영구 포기**된다.
지금 2~3 req/s 라 429 가 안 날 뿐, **나면 조용히 사람이 빠진다.**

### 설계 — 스로틀이 아니라 **예산**을 넣는다

```
[제안 0] 통당 최소 간격 (본부가 말한 "스로틀"). 목적: 레이트리밋 회피.
         -> ★넣지 않는다. 실효 2~3 req/s 로 이미 10 아래다.
            간격을 넣으면 300초 예산만 더 먹어서, 안 나는 사고를 막으려고
            날 사고를 키우는 것이 된다.

[제안 1] ★중복 alreadySent 제거. 목적: 300초 예산 회수. 가장 싸다.
         canSend 가 방금 물어본 것을 executeSend 가 또 묻는다.
         canSend 를 통과했다는 사실을 executeSend 에 넘기면 통당 왕복 5->4.
         450통에서 왕복 450회, 낙관 13초 / 실측기준 47초를 되찾는다.
         ★단 executeSend 의 그 검사는 크론 밖 호출자(프로필/스튜디오 경로)의
         유일한 dedup 이므로 지우면 안 되고, "이미 확인했다" 플래그를
         크론 경로에서만 넘기는 형태여야 한다.

[제안 2] ★틱당 발송 예산 (필수). 목적: 300초 초과를 사고가 아니라 설계로.
         dispatchBatch 에 deadline 을 넘기고, 남은 시간이 임계 아래면
         루프를 깨고 { sent, skipped, deferred } 로 정직하게 보고한다.
         남은 통은 다음 틱이 canSend 로 자연히 이어받는다.
         - 함수 시작 기준 240초 예산 (300 - 60 안전마진)
         - 통당 실측 소요의 이동평균으로 "한 통 더 들어갈까" 판정
         - ★deferred > 0 이면 로그 1줄. 소리 없이 잘리는 것과
           "270통 보냈고 180통 남았다" 는 완전히 다른 상태다.

[제안 3] ★429 를 failed 로 적지 않는다. 목적: 사람이 조용히 빠지는 것 방지.
         지금은 429 -> status='failed' -> 15/30/60/120분 백오프 -> 5회면 포기다.
         429 는 "이 사람에게 보내면 안 된다" 가 아니라 "지금 말고" 다.
         retry-after 를 읽어 한 번 기다렸다 재시도하고, 그래도 429 면
         failed 가 아니라 deferred 로 남겨 다음 틱이 백오프 없이 잡게 한다.
         10 req/s 상향 요청은 불필요하다.
```

★**그리고 이게 가장 중요하다**: 세 경로 다 **한 통도 안 보냈다**는 본부 지적이 맞다.
위 숫자는 전부 **왕복 지연 실측 × 건수**이고, **450통 실주행 측정이 아니다.**
리허설이 첫 실주행이므로, 리허설에서 볼 것은 딱 셋이다 —
**(1) 틱 전체 소요 초, (2) deferred 발생 여부, (3) 429 0건.**
그 셋을 못 재면 위 설계는 계산이지 측정이 아니다.

### ★1,000곡 적재는 이 배포에 안 걸린다

본부 전제: "그 12커밋에 음악 라이브러리 적재가 있다 → 1,000곡 적재가 걸린다."
**절반만 맞다.** 12커밋 안의 음악 관련은 `scripts/gen-library-samples.mjs`(fal 샘플 8곡 생성,
**로컬 실행**)와 `src/fal.ts` 의 `generateMusic()`(참가자용 AI 생성)이다.

**실제 적재 도구는 `src/seed-music.ts` 이고, 이것은 `npm run seed:music` — 로컬 CLI 다.**
로컬 ffprobe 로 길이를 재고, R2 에 올리고, v1m 서명을 찍고, `studio_music_assets` 에 upsert 한다.
**Railway 이미지에서 도는 게 아니다.** 그리고 그 파일은 `66c935f`(07-23) = **13번째 커밋**이라
12건 밖이다.

→ **1,000곡 적재의 관문은 ① DDL 하나뿐이다.** 배포는 관문이 아니다.
배포가 막는 것은 **렌더 시 음악 믹스**(`src/worker.ts:718` 이 `studio_music_assets` 를 읽는다)이고,
그건 적재 다음 문제다. **적재는 ① Run 직후 바로 착수 가능하다.**

★단 `seed-music.ts` 는 지금 새 4컬럼을 **안 쓴다**. 1,000곡을 genre/bpm/sort_order/screening_score
없이 넣으면 큐레이션이 33시간에서 안 줄어든다. **적재 전에 seeder 를 4컬럼 대응으로 고쳐야 한다** —
이것도 배포와 무관한 로컬 스크립트 수정이다.

4. 빌드 로그에서 Dockerfile 의 ffmpeg 핀이 붙는지 확인.

**★배포 확인 신호 — 부팅 로그 한 줄.** 채점 워커의 `SEASON_REQUIRED_STATUS` 문구와 같은 역할이다.
`0b860cc`/`3c2ef62` 가 부팅 시 **이미지의 실제 ffmpeg 버전을 찍고 `EXPECTED_FFMPEG` 와 대조**하게
만들었다(`src/worker.ts:970-979`). 현행 배포본에는 이 줄이 **아예 없다.**

```
배포 전  (그런 줄이 없다)
배포 후  ffmpeg <버전> 을 보고하는 줄 + 불일치 시 경고
```

**한 줄이고, 부팅 즉시 보이고, 잡을 필요가 없다.** 이것이 배포 확인 신호다.

**되돌리기**

- 즉시 멈춤: Railway **Rollback**(있으면). 이미지를 되돌리지 브랜치를 되돌리지 않는다.
- 진짜 되돌리기: 머지커밋이면 `git revert -m 1`, 이미 main 이면 `git revert` 12건 또는
  직전 커밋으로 되돌리는 단일 revert 커밋.

**배포 후 즉시 볼 것**

| 로그 | 정상 | 이상 시 |
|---|---|---|
| ffmpeg 버전 보고 줄 | **새로 나타난다** | 없으면 미배포 |
| ffmpeg 불일치 경고 | **없어야** | 있으면 이미지가 핀과 다르다 → 롤백 |
| `render_jobs` 폴링 | 이전과 동일 | 에러/스택트레이스 있으면 롤백 |
| 진행 중이던 렌더 | 리스 회수로 이어받는다(`9a490a3` claimed_at) | 유실되면 롤백 |

## ★본부 규칙 수령 — "X 에서 안 보인다"

> 레포 부재 · 브랜치 부재 · 타입 부재, 셋 다 DB 부재의 증거가 아니다.
> 일반형 = "X 에서 안 보인다" 는 **"X 가 전부다" 일 때만** 부재의 증거다.
> → 부재를 주장할 때는 **"내가 본 범위가 전부인가"** 를 먼저 답한다.

기억에 갱신했다. 오늘 이 규칙을 4번 적용했고, **2번은 규칙이 없었으면 틀렸을 자리였다**:

1. `scoring_start_at` — 레포 타입에 없다고 컬럼이 없는 게 아니었다. **DB 에 있었다.**
   본부 지적대로 없던 건 `lib/seasons.ts` 한 줄이었다. → SQL 에서 뺐다.
2. `is_fixture` / 결과안내 컬럼 — grep 0건으로 끝내지 않고 **service_role 로 42703 프로브**를
   돌려 부재를 증명했다. 결과안내는 이름 후보 **5개**를 다 쳐봤고, 그 과정에서
   `prelim_released_at` 이 **이미 있다는 걸 발견**했다(marker, 스케줄 아님).
   grep 만 했으면 이름이 겹치는 컬럼을 새로 만들 뻔했다.
3. `seasons_public` — 컬럼을 base 테이블에 추가해도 **뷰에는 안 붙는다.** 뷰는
   `SELECT *` 가 아니라 **66컬럼 고정 목록**이었다(실측). 이걸 안 재고 로비 select 에
   `is_fixture` 를 넣었으면 42703 으로 **홈이 통째로 빈다** — 7월 27일 `studio_music_enabled`
   사고와 같은 모양. → 로비는 이번 커밋에서 **안 건드렸다.**
4. `official_actors` 참조 — 코드 grep 0건이었지만, 부재의 범위를 좁히니
   **R2 오브젝트 키 5개와 CryptoBind 서명 입력**이 나왔다. ③이 커진 이유다.
