## 0. RPC 확인 (최우선 지시대로 먼저)

**결론: `advance_season_finalists` 게이트는 judged_status를 실질적으로 안 본다 — 이미 실측·재현됨.**

- `app/api/cron/season-tick/route.ts:438` 원문을 방금 직접 읽었다:
  ```
  if (!s.scoring_complete_at || nowMs < new Date(s.scoring_complete_at).getTime()) continue
  ```
  RPC를 부르기 전 이 한 줄이 전부다 — **날짜 비교뿐, `scoring_results`/`judged_status` 참조가
  코드에 0건.**
- RPC 본체(`advance_season_finalists` 함수 정의)는 이 세션에서 직접 못 열어봤다 — PostgREST에
  `pg_get_functiondef`류 헬퍼가 없고(`scripts/inspect-weight-policy.mjs`가 이미 같은 시도를
  하다 실패한 기록이 남아 있음), `DATABASE_URL` 같은 직결 커넥션 문자열도 두 레포 `.env`
  어디에도 없다(변수명만 확인, 값 아님). RPC 안에서 추가로 뭔가 검사하는지는 소스 코드로는
  **여전히 확인 못함.**
- **그런데 이미 실측으로 답이 나와 있다** — `reports/jisu_hq_2026-08-31_eod.md` "④채점 미완
  상태에서 결과가 확정된다": *"실제로 재현: TEST-01이 채점 중(재시도 소진 직전)인데 나머지
  15편으로 결과가 확정·발송됨... season-tick을 한 번 더 쳐도 재계산 안 됨(advancements: [],
  no-op)."* — 이건 코드를 읽어서 추정한 게 아니라 **실제로 그 상황을 만들어서 돌려본 결과**다.
  RPC 안에 뭐가 있든, 실측 결과는 "안 막았다"이다.

**정리**: 코드로 봐도(위 한 줄) 실측으로 봐도(08-31 재현) 오늘 상태는 judged_status를
안 본다. **①의 원래 설계("completed 조건을 엄격화하면 게이트가 자동으로 고쳐진다")는 틀렸다
— season-tick의 저 한 줄이 scoring_results를 아예 참조하지 않으므로, judged_status를 아무리
엄격하게 재정의해도 이 게이트는 안 걸린다.** 이 게이트 자체를 고쳐야 한다(별건 착수 시):
`route.ts:438`의 조건에 "이 시즌·라운드의 scorable 대상 전원이 JUDGING_FINAL"을 **추가로**
합치는 것 — 날짜는 트리거로 남기되, 완료의 증거로 안 쓴다. (★설계만 — 이번 문서에서 코드는
안 고친다, 다음 착수 시 최우선 항목으로 못박아 둔다.)

## 1. 구멍 ① — RECHECK 출구가 없었다

**자동 pairwise recheck 설계:**

1. 행이 JUDGING_RECHECK에 들어가면(3개 슬롯 다 `ok`인데 Low-등급 불일치, 또는 슬롯 하나가
   이미 Reserve로 대체됨) — **다음 batch tick에서 자동으로 1회, "어긋난 회사" 하나만 다시
   부른다.** 어긋난 회사 판정은 지난 회차에 쓴 방식과 같되(가장 가까운 두 값을 "합의 쌍"으로
   보고 나머지 1개가 odd), 시즌 중간이라 등수(rank)를 못 쓰므로 **원점수 자체의 편차**로
   바꾼다: 3사 자체가중점수(CD*.30+EX*.45+OR*.25) 중 나머지 둘의 평균과의 절대 편차가 가장
   큰 쪽이 odd. (★절대점수 임계치는 이번 43편 표본만으론 못 정한다 — 시즌 실주행 초기 데이터로
   캘리브레이션 필요, 지금은 "가장 편차가 큰 하나"라는 상대 규칙만 확정.)
2. odd 판정된 벤더를 **프레임 재추출 없이(이미 있는 프레임 재사용)** 같은 프롬프트·temp 0로
   한 번 더 부른다 — 이게 "pairwise recheck"다.
3. 결과 처리:
   - 새 값이 **나머지 둘에 가까워지면** → 노이즈였다고 보고 새 값으로 교체, consensus
     재계산 → 등급이 High/2-of-3면 **JUDGING_FINAL로 승격.** (원래 값과 새 값 둘 다 감사
     로그에 남긴다 — 어느 걸 버렸는지 추적 가능해야 함.)
   - 새 값도 **여전히 벌어지면** → 이건 노이즈가 아니라 **진짜 3사 의견 불일치**로 확정.
     자동 재시도는 **여기서 멈춘다**(무한 recheck 금지 — 자동 recheck은 행당 정확히 1회로
     상한을 둔다).
4. 진짜 불일치가 확정된 행은 **사람이 푸는 경로로 넘긴다** — 새 UI를 만들지 않고 기존
   `RecommendationsPanel.tsx`/`recommendations.ts`의 "failed" 큐와 같은 자리에 새 카테고리
   ("판정 불일치·확인 필요")로 노출한다. admin이 할 수 있는 액션 3가지: (a) 지금 평균값 그대로
   승인 → JUDGING_FINAL, (b) 점수 직접 override(★[[project_scoring_integrity_rules]] — score
   자동, admin 변경 불가 원칙과 충돌하는지는 판단 필요 사항으로 남김, 이번 설계에서 임의로
   못 정함), (c) 3사 전체 재롤(리롤 버튼) → JUDGING_PENDING으로 되돌려 처음부터.
5. **사람이 푸는 경로가 필요한가 — 필요하다.** 자동 recheck 1회로 안 풀리는 진짜 불일치는
   기계가 계속 굴려도 안 풀린다(같은 3사, 같은 프롬프트, 같은 temp 0 — 새로 넣을 정보가
   없다). 사람이 안 보면 그 행은 대표님이 걱정한 그대로 **영원히 JUDGING_RECHECK에 갇힌다.**

## 2. 구멍 ② — Reserve Judge가 아직 없을 때 임시 규칙

**임시 규칙: 아무것도 새로 안 만든다 — Reserve Judge가 없으면 오늘과 완전히 같은 경로로
떨어뜨린다.** 슬롯이 벤더별 재시도 상한을 다 쓰고 대체할 4번째가 없으면, 그 행은 그냥
`judged_status='failed'`로 간다 — **지금 프로덕션이 이미 하고 있는 것과 정확히 동일**하고,
이미 admin 검토 경로(`recommendations.ts`/`RecommendationsPanel.tsx`)가 있다. 즉 ①의 나머지
설계(슬롯 분리, 일시적/영구적 구분, 벤더별 재시도 정책)는 **Reserve Judge가 정해지기 전에도
그대로 배포 가능** — 실패율을 낮추는 효과(불필요한 3사 재시도 제거)는 이미 얻고, 대체 실패
시 결과가 오늘보다 나빠지지 않는다(오늘도 결국 failed로 떨어지는 케이스였다). ②가 정해지면
"failed로 직행" 대신 "Reserve 호출 → 그래도 실패하면 failed"로 한 단계만 끼워 넣으면 된다.

## 3. 규모 계산 확인

주신 산수 확인: 43편 중 2편이 어떤 형태로든 3사 전원 정상 확보 실패(cf_novya=Gemini 영구 거부,
demo_artisan=Gemini 일시 오류) → **2/43 = 4.65%**, 500편 스케일 = **23.3편.**

슬롯 단위로도 봤다: 43편×3사 = 129 슬롯-시도 중 실패 2건 = **1.55%**, 500편×3사=1,500슬롯
스케일 = **23.3슬롯** — 편 단위와 슬롯 단위 추정이 정확히 일치한다. 단 **이건 이번 표본에서
영향받은 두 편이 각각 슬롯 1개씩만 실패했기 때문에 우연히 일치한 것** — 표본이 43편뿐이라
"한 편에서 2사가 동시에 실패하는 경우"를 한 번도 못 봤다. 그런 케이스가 실제로 얼마나
있을지는 이번 데이터로 추정 불가(리스크로만 기록).
